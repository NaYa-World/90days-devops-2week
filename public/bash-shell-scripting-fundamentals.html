1What is Shell Scripting?

A shell script is a text file containing a sequence of commands that the shell interprets and executes line by line. Instead of typing commands one at a time in a terminal, you write them in a file, make it executable, and run it — automating everything from server provisioning to deployment pipelines.

Bash (Bourne Again SHell) is the default shell on most Linux distributions and the standard for DevOps scripting. It extends the original Bourne shell (sh) with features like arrays, arithmetic, and advanced string manipulation.

🔧 Automation

Automate repetitive tasks: deployments, log rotation, backups, monitoring checks, and infrastructure provisioning.

⚡ Glue Language

Bash connects tools together — pipe grep into awk, feed curl output to jq, chain commands with &&. It's the glue of DevOps.

🏗️ Infrastructure as Code

Before Terraform and Ansible, Bash scripts built entire infrastructures. They still power bootstrap scripts, user-data, and init scripts.

🔍 Debugging & Ops

Incident response scripts, health checks, and diagnostic tools are almost always Bash. Every SRE/DevOps team has a scripts/ directory.

🎯 Interview Context "Shell scripting is the Swiss Army knife of DevOps. It's the first tool you reach for when automating a task, the language of CI/CD pipeline steps, and the foundation of every cloud init script. A DevOps engineer who can't write Bash is like a carpenter who can't use a hammer."

2Internal Working

When you execute a Bash script, here's exactly what happens under the hood:

$ ./deploy.sh # User executes the script │ ▼ ┌─────────────────────────────────┐ │ 1. KERNEL CHECKS │ │ • Is the file executable? │ # chmod +x — checks x permission │ • Read shebang line (#!) │ # #!/bin/bash → fork + exec /bin/bash └──────────┬──────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ 2. NEW BASH PROCESS │ │ • fork() — create child process │ │ • Inherits parent environment │ # exported vars, PATH, HOME, etc. │ • Opens script file for reading │ └──────────┬──────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ 3. PARSING (Line by Line) │ │ • Tokenization │ # break into words │ • Variable expansion │ # $VAR → value │ • Command substitution │ # $(cmd) → output │ • Glob expansion │ # *.log → file1.log file2.log │ • Quote removal │ └──────────┬──────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ 4. EXECUTION │ │ • Builtins: execute directly │ # cd, echo, export, read │ • External: fork+exec │ # ls, grep, awk → new process │ • Pipelines: fork each stage │ # cmd1 | cmd2 → 2 processes └──────────┬──────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ 5. EXIT │ │ • Return exit code (0–255) │ # 0 = success, non-zero = failure │ • Run EXIT traps if any │ │ • Child process terminates │ └─────────────────────────────────┘
📘 Key Insight Each external command in a script runs in its own child process (fork+exec). This means cd in a subprocess won't change the parent's directory — which is why cd is a shell builtin, not an external command. Understanding this process model is critical for writing efficient scripts.
🏭 Production Relevance In CI/CD pipelines (Jenkins, GitHub Actions), each run: step spawns a new shell. Variables set in one step don't persist to the next unless you export them to $GITHUB_ENV or use artifacts. This is the fork model in action.
3Script Syntax & Structure
The Shebang Line

Every script starts with a shebang (#!) — it tells the kernel which interpreter to use.

Shebang Options BASH
12345678
#!/bin/bash # Most common — hardcoded path to bash #!/usr/bin/env bash # Portable — finds bash in PATH (recommended) #!/bin/sh # POSIX shell — most portable, fewest features #!/usr/bin/env python3 # Not Bash — but shebangs work for any interpreter # WHY #!/usr/bin/env bash? # On macOS: /bin/bash is v3.2 (2007!), but brew installs bash 5 to /usr/local/bin/bash # env finds the FIRST bash in PATH — which is the modern one if you installed it
Always use #!/usr/bin/env bash for portability across Linux distros and macOS. It resolves the interpreter via PATH rather than hardcoding a location.
Your First Script
hello.sh — Your First Bash Script BASH
12345678910111213
#!/usr/bin/env bash # ────────────────────────────────────── # Script: hello.sh # Purpose: First Bash script — print system info # Author: DevOps Student # Date: 2026-07-21 # ────────────────────────────────────── echo "Hello, DevOps Engineer!" echo "Hostname: $(hostname)" echo "Date: $(date '+%Y-%m-%d %H:%M:%S')" echo "Uptime: $(uptime -p 2>/dev/null || uptime)" echo "Kernel: $(uname -r)"
This script uses command substitution $(command) to embed live system data into the output. The 2>/dev/null || uptime pattern gracefully handles macOS where -p flag may not exist.
Making it Executable
Execute a Script — Three Methods BASH
1234567891011
# Method 1: Make executable + run (RECOMMENDED) chmod +x hello.sh ./hello.sh # Method 2: Explicitly call the interpreter bash hello.sh # Method 3: Source it (runs in CURRENT shell — variables persist!) source hello.sh # or equivalently: . hello.sh
Method 1 is the standard. Method 3 (source) is special — it runs the script in your current shell, so any variables or cd commands affect your session. This is how .bashrc works.
⚠️ Warning Never run source on untrusted scripts! Since it executes in your current shell, it can modify your environment, overwrite variables, or even exit your terminal session.
4Variables & Data Types

Bash variables are untyped by default — everything is a string. There are no integers, floats, or booleans. Bash interprets context to decide if a value is a number or text.

Variable Assignment
Variable Basics BASH
123456789101112131415161718192021
#!/usr/bin/env bash # ── ASSIGNMENT (NO spaces around =) ── NAME="deploy-server" # ✅ Correct PORT=8080 # ✅ Still a string internally NAME = "deploy-server" # ❌ WRONG — bash sees NAME as a command # ── READING VARIABLES ── echo "Server: $NAME" # Simple expansion echo "Server: ${NAME}" # Braces — safer, explicit echo "Port: ${PORT}" # ── WHY BRACES MATTER ── FILE="report" echo "$FILE_final.txt" # ❌ Bash looks for $FILE_final (undefined) echo "${FILE}_final.txt" # ✅ Correctly prints: report_final.txt # ── READONLY VARIABLES ── readonly APP_VERSION="2.4.1" APP_VERSION="3.0" # ❌ ERROR — cannot modify readonly variable
The #1 beginner mistake is putting spaces around =. In Bash, NAME = value tries to run NAME as a command with = and value as arguments.
Quoting Rules
Quote Type Syntax Expansion? Example Output
Double quotes "..." ✅ Variables + commands expanded "Hello $USER" Hello karthik
Single quotes '...' ❌ Nothing expanded (literal) 'Hello $USER' Hello $USER
Backticks `...` ✅ Command substitution (legacy) `date` Mon Jul 21...
$(...) $(...) ✅ Command substitution (modern) $(date) Mon Jul 21...
★ Best Practice Always use $(...) over backticks for command substitution. Backticks don't nest, are hard to read, and look like single quotes in some fonts. $(command) nests cleanly: $(echo $(date)).

Parameter Expansion
Advanced Parameter Expansion BASH
1234567891011121314151617
FILENAME="backup-2026-07-21.tar.gz" # Default values echo "${ENV:-production}" # Use "production" if $ENV is unset/empty echo "${ENV:=production}" # Same + ASSIGN "production" to $ENV # String manipulation echo "${FILENAME%.tar.gz}" # Remove shortest suffix: backup-2026-07-21 echo "${FILENAME%%.*}" # Remove longest suffix: backup-2026-07-21 echo "${FILENAME#*-}" # Remove shortest prefix: 2026-07-21.tar.gz echo "${FILENAME##*-}" # Remove longest prefix: 21.tar.gz # Length and substring echo "${#FILENAME}" # String length: 26 echo "${FILENAME:0:6}" # Substring (offset:length): backup echo "${FILENAME/backup/archive}" # Replace first: archive-2026-07-21.tar.gz echo "${FILENAME^^}" # Uppercase: BACKUP-2026-07-21.TAR.GZ
Parameter expansion replaces the need for external tools like sed, cut, and basename for simple string operations, making scripts faster (no fork overhead).
5Conditionals
if / elif / else
Conditional Syntax BASH
123456789101112131415161718192021
#!/usr/bin/env bash # Health check script for a web service SERVICE_URL="http://localhost:8080/health" HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" "$SERVICE_URL") if [[ "$HTTP_CODE" -eq 200 ]]; then echo "✅ Service is healthy (HTTP $HTTP_CODE)" elif [[ "$HTTP_CODE" -eq 503 ]]; then echo "⚠️ Service unavailable (HTTP $HTTP_CODE) — restarting..." sudo systemctl restart myapp elif [[ "$HTTP_CODE" -eq 000 ]]; then echo "❌ Connection refused — service might be down" sudo systemctl start myapp else echo "⚠️ Unexpected response: HTTP $HTTP_CODE" fi # Exit with non-zero if unhealthy (for CI/CD pipelines) [[ "$HTTP_CODE" -eq 200 ]] || exit 1
Use [[ ]] (double brackets) instead of [ ] — it's a Bash builtin that supports regex, pattern matching, and doesn't require quoting variables to prevent word splitting.

6Loops
for Loop
for Loop — Iterate Over Items BASH
1234567891011121314151617181920212223
#!/usr/bin/env bash # ── Iterate over a list ── for server in web-01 web-02 api-01 db-01; do echo "Deploying to $server..." # ssh "$server" 'sudo systemctl restart app' done # ── Iterate over files ── for logfile in /var/log/app/*.log; do echo "Compressing: $logfile" gzip "$logfile" done # ── C-style for loop (counters) ── for (( i=1; i<=5; i++ )); do echo "Attempt $i of 5" done # ── Iterate over command output ── for user in $(awk -F: '$3 >= 1000 {print $1}' /etc/passwd); do echo "Human user: $user" done
Always quote variables in loops: "$logfile" not $logfile. Files with spaces in names will break unquoted loops. Use glob patterns over ls output — parsing ls is fragile.
while Loop
while Loop — Retry Until Success BASH
123456789101112131415161718
#!/usr/bin/env bash # Wait for a service to become ready (common in Docker/K8s) MAX_RETRIES=30 RETRY_INTERVAL=2 attempt=0 while [[ $attempt -lt $MAX_RETRIES ]]; do if curl -sf http://localhost:5432/health >/dev/null 2>&1; then echo "✅ Database is ready! (attempt $((attempt+1)))" exit 0 fi echo "⏳ Waiting for database... (attempt $((attempt+1))/$MAX_RETRIES)" sleep "$RETRY_INTERVAL" (( attempt++ )) done echo "❌ Database failed to start after $MAX_RETRIES attempts" >&2; exit 1
This is the standard "wait-for-it" pattern used in Docker entrypoint scripts and Kubernetes init containers. It retries a health check with exponential backoff until the dependency is ready.
🏭 Production Pattern This exact retry pattern powers tools like wait-for-it.sh and dockerize. In production, add exponential backoff: sleep $((RETRY_INTERVAL * attempt)) instead of a fixed interval to avoid hammering the target service.
7Functions
Function Syntax & Patterns BASH
1234567891011121314151617181920212223242526272829303132
#!/usr/bin/env bash # ── LOGGING FUNCTION (used in every production script) ── log() { local level="$1"; shift local message="$*" local timestamp=$(date '+%Y-%m-%d %H:%M:%S') echo "[$timestamp] [${level^^}] $message" } # ── USAGE ── log info "Deployment started" log warn "Disk usage at 85%" log error "Connection to database failed" # ── FUNCTION WITH RETURN VALUE ── is_port_open() { local host="$1" local port="$2" nc -z -w3 "$host" "$port" 2>/dev/null return $? # Return nc's exit code (0=open, 1=closed) } # ── USAGE ── if is_port_open "db.internal" 5432; then log info "PostgreSQL is reachable" else log error "PostgreSQL is NOT reachable on port 5432" exit 1 fi # Output: [2026-07-21 23:45:12] [INFO] PostgreSQL is reachable
local makes variables scoped to the function — without it, variables leak into the global scope. Always use local for function variables. The ${level^^} syntax converts to uppercase.
💡 Tip Bash functions don't truly "return" values like other languages. return sets the exit code (0-255). To return strings, use echo and capture with $(function_name). For example: result=$(get_hostname).

9Error Handling
The Holy Trinity of Safe Bash BASH
123456789101112131415161718
#!/usr/bin/env bash set -euo pipefail # ← PUT THIS IN EVERY PRODUCTION SCRIPT # What each flag does: # -e (errexit) → Exit immediately if any command fails (non-zero exit) # -u (nounset) → Exit if an undefined variable is used # -o pipefail → Pipeline fails if ANY command in pipe fails # (normally only the LAST command's exit code matters) # ── WITHOUT pipefail (DANGEROUS) ── # curl http://bad-url | grep "OK" → exit code 0 (grep succeeds on empty input) # ── WITH pipefail (SAFE) ── # curl http://bad-url | grep "OK" → exit code 7 (curl's failure propagates) # Optional: Debug mode # set -x → Print each command before executing (noisy but useful) # set -euxo pipefail → Full debug + safety mode
set -euo pipefail is the most important line in production Bash. Without it, scripts silently continue after failures, which can cause data loss, partial deployments, or security breaches.
trap — Cleanup on Exit
trap — Guaranteed Cleanup BASH
12345678910111213141516171819
#!/usr/bin/env bash set -euo pipefail # Create a temp directory — GUARANTEED to be cleaned up TMPDIR=$(mktemp -d) cleanup() { echo "🧹 Cleaning up temp dir: $TMPDIR" rm -rf "$TMPDIR" } # trap runs cleanup on: normal exit, Ctrl+C, kill, or error trap cleanup EXIT # ── Do work in temp dir ── cd "$TMPDIR" curl -sLO "https://releases.example.com/v2.0/binary.tar.gz" tar xzf binary.tar.gz sudo mv binary /usr/local/bin/ # cleanup() runs automatically — even if tar or mv fails!
trap cleanup EXIT ensures your cleanup function runs no matter how the script exits — success, failure, Ctrl+C, or kill. This prevents temp file leaks on production servers.
⚠️ Warning Never use /tmp/myfile with a predictable name in production scripts — it's a security vulnerability (symlink attacks). Always use mktemp which generates random names like /tmp/tmp.a3xK9Bn2.

Disk Usage Alert Script BASH

#!/usr/bin/env bash set -euo pipefail THRESHOLD=80 LOG_FILE="/var/log/disk-alert.log" log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "$LOG_FILE" } alert_sent=false while IFS= read -r line; do usage=$(echo "$line" | awk '{print $5}' | tr -d '%') mount=$(echo "$line" | awk '{print $6}') if [[ "$usage" -ge "$THRESHOLD" ]]; then log "⚠️ WARNING: $mount is at ${usage}% (threshold: ${THRESHOLD}%)" alert_sent=true fi done < <(df -h | awk 'NR>1 && $5+0 > 0') if [[ "$alert_sent" == "true" ]]; then log "📧 Sending alert notification..." # curl -X POST "$SLACK_WEBHOOK" -d '{"text":"Disk usage alert!"}' else log "✅ All filesystems below ${THRESHOLD}% — healthy" fi

13Production Examples
Production Deploy Script BASH
123456789101112131415161718192021222324252627282930313233343536373839404142434445464748495051525354555657585960
#!/usr/bin/env bash # ────────────────────────────────────────────────────────── # deploy.sh — Zero-downtime deployment with rollback # Usage: ./deploy.sh <version> [environment] # ────────────────────────────────────────────────────────── set -euo pipefail # ── Configuration ── readonly APP_NAME="myapp" readonly DEPLOY_DIR="/opt/${APP_NAME}" readonly RELEASES_DIR="${DEPLOY_DIR}/releases" readonly CURRENT_LINK="${DEPLOY_DIR}/current" readonly VERSION="${1:?Usage: $0 [env]}" readonly ENV="${2:-production}" readonly RELEASE_PATH="${RELEASES_DIR}/${VERSION}" # ── Logging ── log() { echo "[$(date -u '+%Y-%m-%dT%H:%M:%SZ')] [${1^^}] ${*:2}"; } info() { log info "$@"; } error() { log error "$@" >&2; } # ── Cleanup ── trap 'error "Deploy FAILED at line $LINENO"; rollback' ERR rollback() { if [[ -L "${CURRENT_LINK}.previous" ]]; then info "Rolling back to previous release..." ln -sfn "$(readlink "${CURRENT_LINK}.previous")" ""${CURRENT_LINK}" sudo systemctl restart "$APP_NAME" info "Rollback complete" fi } # ── Validate ── info "Starting deploy: v$VERSION → $ENV" [[ -d "$RELEASES_DIR" ]] || mkdir -p "$RELEASES_DIR" # ── Download & Extract ── info "Downloading release artifact..." mkdir -p "$RELEASE_PATH" curl -sfL "https://releases.example.com/$APP_NAME/$VERSION.tar.gz" | tar xzf - -C "$RELEASE_PATH" # ── Save current release for rollback ── if [[ -L "$CURRENT_LINK" ]]; then cp -P "$CURRENT_LINK" "${CURRENT_LINK}.previous" fi # ── Atomic symlink switch (zero downtime) ── info "Switching symlink..." ln -sfn "$RELEASE_PATH" "$CURRENT_LINK" # ── Restart & Health Check ── sudo systemctl restart "$APP_NAME" sleep 3 if curl -sf http://localhost:8080/health >/dev/null; then info "✅ Deploy successful: v$VERSION is live!" else error "Health check failed — triggering rollback" rollback exit 1 fi
This script demonstrates real production patterns: atomic symlink deployment (no downtime), automatic rollback on failure, structured logging, trap ERR for error handling, and health check verification after deploy.
★ Production Pattern: Symlink Deploy The ln -sfn $NEW_RELEASE /opt/app/current pattern is how Capistrano, Deployer, and many deployment tools work. The symlink switch is atomic — there's no moment where the app is "between" versions. This is the gold standard for zero-downtime deployments.

19Interview Questions
Q1 What does set -euo pipefail do and why is it important?
-e (errexit): Script exits immediately when any command returns a non-zero exit code, preventing cascading failures.

-u (nounset): Treats unset variables as errors, catching typos like $SEVER instead of $SERVER that would otherwise silently expand to empty string.

-o pipefail: A pipeline's exit code is the last non-zero code from any command in the pipe, not just the final command. Without this, curl http://bad | grep OK succeeds even when curl fails.

Why it matters: Without these flags, scripts silently continue after failures, which in production can cause partial deployments, data corruption, or security breaches. It's the single most important line in production Bash.
Q2 What's the difference between $@ and $*?
Both expand to all positional parameters, but they behave differently when quoted:

"$@" → Expands to "$1" "$2" "$3" — each argument remains a separate word. This preserves arguments with spaces correctly.

"$*" → Expands to "$1 $2 $3" — all arguments merge into a single string separated by the first character of IFS.

Rule: Always use "$@" when passing arguments to other commands. $* is only useful when you deliberately want to join all arguments into one string.
Q3 Explain the difference between ./script.sh and source script.sh.
./script.sh: Creates a new child process (fork+exec). The script runs in a subshell with its own environment. Variables set inside do NOT affect the parent shell. The parent waits for the child to finish and receives its exit code.

source script.sh (or . script.sh): Executes the script in the CURRENT shell. Every command runs as if you typed it directly. Variables, cd changes, exports, and functions all persist in your session.

Use case: source is used for loading configuration files like .bashrc, .env files, and function libraries. ./script.sh is used for running independent scripts.
Q4 How would you handle secrets in a Bash script?
Never hardcode secrets. Production approaches:

1. Environment variables: export DB_PASS=$(aws secretsmanager get-secret-value ...)
2. .env files: source .env with .env in .gitignore
3. Secret managers: AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager
4. Runtime injection: Kubernetes Secrets mounted as env vars or files
5. Avoid: command-line arguments (visible in ps aux), scripts committed to Git, environment that persists in logs

Key rule: Secrets should never appear in ps output, shell history, or Git history.
Q5 What is a trap in Bash? Give a production example.
trap registers a function or command to run when a specific signal is received. Common signals:

EXIT: Runs on any exit (normal or error) — used for cleanup
ERR: Runs when a command fails (with set -e) — used for error logging
INT: Runs on Ctrl+C — used for graceful shutdown
TERM: Runs on kill — used for cleanup before termination

Production example: A deployment script creates a temp directory, downloads artifacts, and deploys. trap cleanup EXIT ensures the temp directory is always deleted, even if the script crashes mid-deploy — preventing disk space leaks on production servers.

Q3: Why can't you just rm a large log file to free space?
Write your answer here before revealing the model answer...

📖 Model Answer

▶

If a process has the file open (e.g., syslog, nginx), the inode isn't released until the process closes the file descriptor. rm removes the directory entry but the disk blocks remain allocated. You'd see df still showing 95% even after deleting.

Solutions: (1) truncate -s 0 /var/log/file.log empties it without changing the inode, (2) logrotate --force rotates it properly, (3) restart the service that holds the fd open, or (4) lsof | grep deleted to find zombie file handles.

21Common Mistakes
❌ Mistake 1: Spaces around = in assignment NAME = "server" → Bash tries to run NAME as a command. Fix: NAME="server" (no spaces).
❌ Mistake 2: Unquoted variables rm $FILE → If $FILE is empty, this becomes rm (no args). If it has spaces, it splits into multiple files. Fix: rm "$FILE".
❌ Mistake 3: Using [ ] instead of [[ ]] [ $VAR == "test" ] → Fails if $VAR is empty (syntax error). Fix: [[ "$VAR" == "test" ]] — double brackets handle empty vars safely.
❌ Mistake 4: Parsing ls output for f in $(ls *.txt) → Breaks on filenames with spaces. Fix: for f in *.txt — globs are safer and faster.
❌ Mistake 5: Ignoring exit codes Not checking if curl, tar, or cp succeeded. A deploy script that doesn't check exit codes can deploy broken artifacts. Fix: Use set -e or check $? explicitly.
❌ Mistake 6: Using backticks for command substitution VAR=`echo $(date)` → Backticks don't nest well, are hard to read. Fix: VAR=$(echo $(date)).
22Best Practices
★ 1. Always Start With set -euo pipefail This single line prevents 90% of silent failures in production scripts. Make it a muscle memory habit.
★ 2. Quote All Variables "$VAR" not $VAR. The only exception is inside [[ ]] on the left side of ==, but even there, quoting doesn't hurt.
★ 3. Use Functions for Reusable Logic Even in scripts under 50 lines, functions improve readability. Name them clearly: validate_input(), deploy_release(), send_notification().
★ 4. Use local Variables in Functions local var="value" prevents variable leakage. Global state in Bash is the #1 cause of subtle bugs in longer scripts.
★ 5. Log Everything With Timestamps Use a log() function that prepends ISO 8601 timestamps. When debugging a 3 AM incident, timestamps are essential.
★ 6. Use trap EXIT for Cleanup Temp files, lock files, mounted volumes — always clean up. trap cleanup EXIT is your guarantee.
★ 7. Validate All Inputs at the Top Check argument count, file existence, permissions, and required tools BEFORE doing any work. Fail fast, fail clearly.
★ 8. Use shellcheck shellcheck script.sh catches bugs that humans miss. Integrate it into your CI pipeline: shellcheck --severity=warning scripts/*.sh.

  • Bash scripts automate repetitive DevOps tasks — deployments, monitoring, backups, provisioning
