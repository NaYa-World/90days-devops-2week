CI/CD Fundamentals

Understand the philosophy behind Continuous Integration and Continuous Delivery — the backbone of modern DevOps pipelines.

CORE CONCEPT THEORY

What Problem Does CI/CD Solve?

Before CI/CD, teams merged large features every few weeks — called "integration hell". Bugs piled up, builds broke unpredictably, and deployments were high-risk, manual events that everyone feared.

Core Insight: The longer you wait to integrate code, the harder it becomes. CI/CD forces small, frequent integrations so bugs surface early when they're cheap to fix.

Continuous Integration (CI)

Developers push code to a shared repository multiple times a day. An automated pipeline immediately:

  1. Compiles and builds the code
  2. Runs unit and integration tests
  3. Checks code quality (linting, SAST)
  4. Publishes a build artifact

If any step fails, the developer is notified within minutes — not days.

Continuous Delivery vs. Continuous Deployment

Continuous Delivery

Every commit is releasable. Deployments to production still require a human approval step (a button click or merge to main).

Human Gate

Continuous Deployment

Every commit that passes all tests is automatically deployed to production. No human intervention required.

Full Automation

Jenkins Installation on AWS EC2

Module 5 · Lesson 2

Deploy a production-ready Jenkins master on an AWS EC2 instance with proper Java, firewall, and systemd configuration.

Step 1 — Launch EC2 Instance

  • AMI: Ubuntu 22.04 LTS or Amazon Linux 2023
  • Instance Type: t3.medium (minimum for production: t3.large)
  • Storage: 20 GB gp3 root volume + 50 GB for workspace
  • Security Group: Allow ports 8080 (Jenkins UI), 22 (SSH), 50000 (agent JNLP)

Step 2 — Install Java 17

Jenkins requires Java 17 (LTS) or Java 21 as of Jenkins 2.436+.

sudo apt update
sudo apt install -y fontconfig openjdk-17-jre
java -version   # should show: openjdk 17.x.x

Step 3 — Add Jenkins Repository and Install

# Add Jenkins GPG key and repo
sudo wget -O /usr/share/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key

echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc]" \
  https://pkg.jenkins.io/debian-stable binary/ | \
  sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null

sudo apt update
sudo apt install -y jenkins

Step 4 — Start and Enable Jenkins

sudo systemctl enable jenkins
sudo systemctl start jenkins
sudo systemctl status jenkins   # verify it's Active (running)

Step 5 — Unlock Jenkins

# Get the initial admin password
sudo cat /var/lib/jenkins/secrets/initialAdminPassword

Navigate to http://<EC2-PUBLIC-IP>:8080, enter the password, and follow the setup wizard to install suggested plugins.

Production Tip: Never expose Jenkins on port 8080 directly in production. Put Nginx as a reverse proxy in front of it with TLS/HTTPS via Let's Encrypt or AWS ACM.

Essential Post-Install Configuration

  • Create an admin user (not the default one)
  • Set Jenkins URL in Manage Jenkins → System → Jenkins URL
  • Configure executors: set master to 0 executors (builds should run on agents)
  • Enable CSRF Protection (enabled by default in Jenkins 2.x)
  • Enable Script Security (Groovy sandbox)

Jenkins Architecture (Master/Agent)

Module 5 · Lesson 3

Understand how Jenkins scales builds across distributed agent nodes using the master/agent (controller/agent) model.

The Controller (Master)

The Jenkins controller is the brain of the operation. It is responsible for:

  • Serving the web UI and REST API
  • Storing configuration, credentials, and job definitions
  • Scheduling builds on agents
  • Recording build results and artifacts

Critical Rule: Never run builds on the master/controller in production. Set its executor count to 0. This keeps the master stable and prevents resource exhaustion from build jobs.

Agents (Workers)

Agents are machines that execute the actual build steps. They connect to the master via:

SSH Agent

Master SSH into the agent server. Simplest setup for Linux agents. Uses the Jenkins master's SSH credentials.

Recommended

JNLP / TCP Agent

Agent initiates the connection to master on port 50000. Better for cloud or firewall-restricted environments.

Cloud-Friendly

Labels and Isolation

Agents are tagged with labels so pipelines can target the correct build environment:

pipeline {
    agent { label 'linux-docker' }  // only run on agents labelled linux-docker
    ...
}

Dynamic Agents with Kubernetes

In cloud-native environments, Jenkins uses the Kubernetes Plugin to spin up ephemeral pod agents for each build and destroy them when done — no idle agent cost.

This is the modern approach: Jenkins controller on a persistent pod, build agents as ephemeral pods using a podTemplate definition in the Jenkinsfile.

Declarative Pipeline

Module 5 · Lesson 5

Master the Declarative Pipeline syntax — the modern, structured way to define Jenkins pipelines as code using a Jenkinsfile.

Anatomy of a Declarative Jenkinsfile

pipeline {
    agent { label 'linux' }           // Where to run

    environment {                     // Environment variables
        MAVEN_OPTS = '-Xmx512m'
        SONAR_TOKEN = credentials('sonar-token')
    }

    tools {                           // Auto-install tools
        maven 'Maven-3.9'
        jdk 'JDK-17'
    }

    options {
        timeout(time: 30, unit: 'MINUTES')
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '10'))
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean compile -DskipTests'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
            post {
                always {
                    junit '**/target/surefire-reports/*.xml'
                }
            }
        }

        stage('Code Analysis') {
            steps {
                withSonarQubeEnv('SonarCloud') {
                    sh 'mvn sonar:sonar'
                }
            }
        }

        stage('Quality Gate') {
            steps {
                timeout(time: 5, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true
                }
            }
        }

        stage('Package') {
            steps {
                sh 'mvn package -DskipTests'
                archiveArtifacts artifacts: 'target/*.jar'
            }
        }

        stage('Deploy') {
            when { branch 'main' }
            steps {
                sshagent(['deploy-key']) {
                    sh 'scp target/*.jar user@server:/app/'
                }
            }
        }
    }

    post {
        success {
            slackSend channel: '#builds', color: 'good', message: "✅ ${env.JOB_NAME} #${env.BUILD_NUMBER} passed!"
        }
        failure {
            slackSend channel: '#builds', color: 'danger', message: "❌ ${env.JOB_NAME} #${env.BUILD_NUMBER} FAILED!"
        }
        always {
            cleanWs()
        }
    }
}

Key Declarative Directives

DirectivePurpose
agentDefines where the pipeline (or stage) runs
environmentSets env vars; use credentials() to inject secrets
toolsAuto-installs configured tools (Maven, JDK, etc.)
optionsPipeline-level settings (timeouts, concurrency, log rotation)
whenConditional execution (branch name, environment, etc.)
parallelRuns multiple stages simultaneously on different agents
postActions that always run after stages (cleanup, notifications)

Parallel Stages

stage('Test in Parallel') {
    parallel {
        stage('Unit Tests') {
            steps { sh 'mvn test -pl :unit-tests' }
        }
        stage('Integration Tests') {
            agent { label 'integration' }
            steps { sh 'mvn verify -pl :integration-tests' }
        }
    }
}

GitHub Integration

Module 5 · Lesson 6

Connect Jenkins to GitHub for automated pipeline triggers via webhooks and SCM polling.

Step 1 — GitHub Personal Access Token

Create a GitHub PAT with these scopes: repo, admin:repo_hook, read:user.

Add it to Jenkins: Manage Jenkins → Credentials → System → Global → Add Credential → Kind: Username with password (username: your GitHub username, password: the PAT).

Step 2 — Configure GitHub Server in Jenkins

In Manage Jenkins → System → GitHub Servers, add a new server pointing to https://api.github.com and associate your credentials.

Step 3 — Webhook Setup

In your GitHub repository settings, add a webhook:

  • Payload URL: http://<JENKINS_URL>/github-webhook/
  • Content type: application/json
  • Events: Push events + Pull request events

The trailing slash in /github-webhook/ is required. Jenkins will return 302 without it, causing webhook delivery failures.

Step 4 — Multibranch Pipeline Job

A Multibranch Pipeline automatically creates child pipeline jobs for every branch and PR in your repository that contains a Jenkinsfile.

  • Create a Multibranch Pipeline item in Jenkins
  • Set Branch Source: GitHub, authenticate with your credentials
  • Set Build Configuration: by Jenkinsfile (Script Path: Jenkinsfile)
  • Enable automatic branch indexing (scan every 1 hour or on webhook)

SCM Polling vs. Webhooks

Webhooks

GitHub pushes events to Jenkins the instant a push happens. Near-zero latency. Preferred for production.

Recommended

SCM Polling

Jenkins polls GitHub on a cron schedule. Use when Jenkins is behind a firewall and GitHub can't reach it.

H/5 * * * * = every 5 minutes

Shared Libraries

Module 5 · Lesson 7

Eliminate Jenkinsfile duplication across 50+ repos with Shared Libraries — centralized Groovy code reusable across all pipelines.

Why Shared Libraries?

Without shared libraries, every Jenkinsfile copies the same deploy logic. A bug fix means updating 50 files. With shared libraries, you fix it once.

Required Directory Structure

jenkins-shared-library/           # GitHub repo
├── vars/                         # Global variables (auto-loaded)
│   ├── buildMaven.groovy         # callable as buildMaven() in Jenkinsfile
│   ├── deployToK8s.groovy
│   └── notifySlack.groovy
├── src/                          # Groovy classes (use @Library to import)
│   └── com/company/
│       ├── Build.groovy
│       └── Deploy.groovy
└── resources/                   # Non-Groovy files (shell scripts, configs)
    └── scripts/
        └── health-check.sh

Example: vars/buildMaven.groovy

// vars/buildMaven.groovy
def call(Map config = [:]) {
    def jdkVersion = config.jdk ?: 'JDK-17'
    def mavenVersion = config.maven ?: 'Maven-3.9'
    def skipTests = config.skipTests ?: false

    withEnv(["JAVA_HOME=${tool jdkVersion}"]) {
        sh "mvn clean ${skipTests ? 'package -DskipTests' : 'verify'}"
    }
}

Using the Library in a Jenkinsfile

@Library('my-shared-library@main') _

pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                buildMaven(jdk: 'JDK-17', skipTests: false)
            }
        }
        stage('Deploy') {
            steps {
                deployToK8s(namespace: 'production', image: 'myapp:latest')
            }
        }
    }
    post {
        always {
            notifySlack(channel: '#deployments')
        }
    }
}

Registering the Shared Library

In Manage Jenkins → System → Global Pipeline Libraries:

  • Name: my-shared-library (this is the name used in @Library)
  • Default version: main
  • Retrieval method: Modern SCM → GitHub
  • Check "Load implicitly" if you want all pipelines to have access without @Library

Security: Shared library code runs outside the Groovy sandbox by default. Review all library code carefully — it has full access to Jenkins APIs and the filesystem.

P1 Incident Simulation — Troubleshooting Failed Builds

Module 5 · Lesson 8

Real-world troubleshooting methodology for production pipeline failures. Every DevOps engineer faces these — know them cold.

P1 = Production is down or blocked. The deployment pipeline is broken. No releases can go out. SLA clock is ticking.

Incident Response Checklist

  1. Check the console output — Read the full build log, not just the summary. The error is usually 10–20 lines before "BUILD FAILURE".
  2. Identify the failing stage — Which stage is red in the Stage View?
  3. Check recent changes — What changed since the last green build? (git log --oneline -10)
  4. Check agent health — Is the agent node online? Disk space? CPU?
  5. Check Jenkins system logs — Manage Jenkins → System Log
  6. Verify credentials — Did a token expire? Certificate expire?
  7. Check external dependencies — Is the Maven repo / Docker registry reachable?

Common Failure Patterns

Error PatternRoot CauseFix
Connection refused :8080Jenkins agent can't reach controllerCheck Security Group / firewall, port 50000
Could not resolve artifactMaven repo unreachable or privateCheck settings.xml, network, repo credentials
Permission denied (publickey)SSH key missing or wrong userAdd SSH key to jenkins user's authorized_keys
java.io.IOException: error=12Out of memory on agentIncrease agent heap or add swap space
No space left on deviceAgent disk full from build artifactsRun cleanWs(), prune old workspaces
CSRF check failedWebhook has wrong URL or missing trailing slashFix webhook URL, check Jenkins CSRF settings
Stage hung / timeoutDeadlock, infinite wait, or test not finishingAdd timeout() block, check for blocking I/O

Rollback Strategy

// Emergency rollback: re-run the last successful build
// 1. Find last green build number in Jenkins UI
// 2. Open that build → Replay (runs exact same Jenkinsfile + params)
// OR use parameterized pipeline:

parameters {
    string(name: 'DEPLOY_TAG', defaultValue: 'latest', description: 'Docker image tag to deploy')
}
// Emergency: set DEPLOY_TAG to last known-good tag
// This gives you a 1-click rollback

Post-Incident: Blameless Retrospective

  • Timeline: Exact sequence of events from first alert to resolution
  • Root Cause: What actually caused it (not the symptom)
  • Contributing Factors: What made it worse or harder to diagnose
  • Action Items: Concrete tasks with owners and due dates to prevent recurrence
  • Detection Gap: How can we catch this faster next time?

Professional Mindset: The best DevOps engineers don't avoid failures — they build systems that recover fast and learn from every incident. Speed of recovery > prevention of all failures.
