Maven Build Tool Fundamentals

Master Maven — the standard Java build tool used in 80% of Indian enterprise projects. From POM structure to multi-module builds and CI/CD integration.

1What is Maven?

Maven is a build automation and project management tool for Java projects. It standardises how projects are built, tested, and packaged — eliminating the "works on my machine" problem across development teams.

In the Indian IT context, you'll encounter Maven in every Spring Boot, Spring MVC, or Java EE project at Infosys, TCS, Wipro, and in product companies like Razorpay. A DevOps engineer who can't read a pom.xml is blocked from debugging 90% of Java CI pipeline failures.

📦 Build Automation

Compile, test, package, and deploy Java applications with a single command. No more manual javac chains.

🔗 Dependency Management

Declare dependencies in pom.xml; Maven downloads them from central repositories automatically. No JAR copying.

🏗️ Convention over Config

Standard project layout: src/main/java, src/test/java. Every Maven developer instantly knows where to look.

🔌 Plugin Ecosystem

1000+ plugins extend Maven — from code coverage (JaCoCo) to static analysis (Checkstyle, SpotBugs) to Docker builds.

🏢 Multi-Module Support

Parent POM coordinates dozens of child modules — essential for microservices monorepos at scale.

🔄 CI/CD Native

Jenkins, GitHub Actions, and every major CI tool has first-class Maven support. mvn clean install is universally understood.

📌 Maven vs GradleIn Indian enterprises: Maven is the default for Spring Boot/Java EE projects built pre-2018. Gradle is common in Android and newer microservice stacks. A Senior DevOps Engineer needs to know both. This module is Maven; Gradle follows in Module 08.
Standard Directory Structure
Maven Project LayoutTREE
my-app/ ├── pom.xml # Project Object Model — the heart of Maven ├── src/ │ ├── main/ │ │ ├── java/ # Production Java source code │ │ └── resources/ # application.properties, logback.xml │ └── test/ │ ├── java/ # JUnit/TestNG test classes │ └── resources/ # test-specific configs └── target/ # BUILD OUTPUT — never commit this to Git ├── classes/ # compiled .class files ├── my-app-1.0.jar # packaged artifact └── surefire-reports/ # test results XML
⚡ The target/ directory is Maven's output. Add it to .gitignore. Every mvn clean deletes it.
2Installation & Setup
Install Maven on Amazon Linux 2023 / EC2BASH
# Check if Java is installed first (Maven requires JDK, not JRE) java -version javac -version # Install Java 17 (LTS) if missing sudo dnf install java-17-amazon-corretto-devel -y # Install Maven from dnf (Amazon Linux 2023) sudo dnf install maven -y # Verify installation mvn --version # Expected output: # Apache Maven 3.8.x ... # Java version: 17.x.x # Check JAVA_HOME is set correctly echo $JAVA_HOME # If JAVA_HOME is missing, add to ~/.bashrc: echo 'export JAVA_HOME=$(dirname $(dirname $(readlink -f $(which javac))))' >> ~/.bashrc echo 'export PATH=$JAVA_HOME/bin:$PATH' >> ~/.bashrc source ~/.bashrc
⚡ Maven needs the JDK (Java Development Kit), not just the JRE. Installing only JRE breaks the compile phase.
Create Your First Maven Project
Generate Project from ArchetypeBASH
# Generate a basic Java project mvn archetype:generate \ -DgroupId=com.devops.demo \ -DartifactId=my-app \ -DarchetypeArtifactId=maven-archetype-quickstart \ -DarchetypeVersion=1.4 \ -DinteractiveMode=false # Navigate into the project cd my-app # Build it immediately mvn clean package # Run the JAR java -jar target/my-app-1.0-SNAPSHOT.jar
Essential Maven Commands

3POM — Project Object Model

The pom.xml is the single source of truth for a Maven project. Every Maven action reads from it. A DevOps engineer who can't navigate a pom.xml cannot diagnose CI build failures.

Production-Grade pom.xml — AnnotatedXML
<?xml version="1.0" encoding="UTF-8"?> <project xmlns="http://maven.apache.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd"> <modelVersion>4.0.0</modelVersion> <!-- Always 4.0.0 --> <!-- ═══ PROJECT COORDINATES ═══ --> <groupId>com.company.team</groupId> <!-- reverse-DNS org --> <artifactId>payment-service</artifactId> <!-- unique project name --> <version>1.2.3-SNAPSHOT</version> <!-- SNAPSHOT=in development --> <packaging>jar</packaging> <!-- jar | war | pom | ear --> <!-- ═══ PROPERTIES — centralise versions ═══ --> <properties> <java.version>17</java.version> <spring-boot.version>3.2.0</spring-boot.version> <maven.compiler.source>${java.version}</maven.compiler.source> <maven.compiler.target>${java.version}</maven.compiler.target> <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding> </properties> <!-- ═══ DEPENDENCIES ═══ --> <dependencies> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> <version>${spring-boot.version}</version> </dependency> <!-- TEST scope: only available during test phase --> <dependency> <groupId>org.junit.jupiter</groupId> <artifactId>junit-jupiter</artifactId> <version>5.10.0</version> <scope>test</scope> <!-- compile | test | provided | runtime | system --> </dependency> <!-- PROVIDED scope: container provides at runtime (Tomcat, etc) --> <dependency> <groupId>javax.servlet</groupId> <artifactId>javax.servlet-api</artifactId> <version>4.0.1</version> <scope>provided</scope> </dependency> </dependencies> <!-- ═══ BUILD PLUGINS ═══ --> <build> <plugins> <!-- Spring Boot fat JAR --> <plugin> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-maven-plugin</artifactId> </plugin> <!-- Code coverage --> <plugin> <groupId>org.jacoco</groupId> <artifactId>jacoco-maven-plugin</artifactId> <version>0.8.11</version> <executions> <execution> <goals><goal>prepare-agent</goal></goals> </execution> <execution> <id>report</id> <phase>test</phase> <goals><goal>report</goal></goals> </execution> </executions> </plugin> </plugins> </build> </project>
⚡ The GAV coordinates (groupId + artifactId + version) are Maven's unique identifier for every artifact in the universe. Think of them as the package address.
Dependency Scopes
Scope Compile Test Runtime Packed into JAR Use Case
compile (default) ✅ ✅ ✅ ✅ Spring Boot, Lombok, etc.
test ❌ ✅ ❌ ❌ JUnit, Mockito, AssertJ
provided ✅ ✅ ❌ ❌ Servlet API (Tomcat provides it)
runtime ❌ ✅ ✅ ✅ JDBC drivers, logging impl
system ✅ ✅ ❌ ❌ Local JAR (avoid in prod)
🎤 Top Interview TrapInterviewers love asking: "What's the difference between provided and test?" The key: provided is available at compile time but not packaged; test is never available in production. Swap them and your servlet-api ends up in your WAR, causing ClassCastException in Tomcat.
4Build Lifecycle

Maven has 3 built-in lifecycles. Each lifecycle is a sequence of phases. Running a phase runs every phase before it first — this is what trips up beginners.

Default Lifecycle (most important)
Phase What Happens
validate Check POM is correct
compile Compile src/main/java
test-compile Compile src/test/java
test Run unit tests (Surefire)
package Create JAR/WAR in target/
verify Run integration tests
install Copy to ~/.m2/repository
deploy Push to remote Nexus/Artifactory
Clean & Site Lifecycles
📌 Clean Lifecyclepre-clean → clean → post-clean
Run with: mvn clean
Deletes target/ directory.
📌 Site Lifecyclepre-site → site → post-site → site-deploy
Run with: mvn site
Generates project documentation website.
⚠️ Common Mistakemvn package runs compile + test + package. If your test environment is broken, mvn package fails. Use mvn package -DskipTests to bypass during debugging — never in production CI.
DEFAULT LIFECYCLE FLOW ══════════════════════════════════════════════════════════════ mvn package: ┌──────────┐ ┌─────────┐ ┌───────────┐ ┌──────┐ ┌─────────┐ │ validate │──▶│ compile │──▶│ test │──▶│verify│──▶│ package │ └──────────┘ └─────────┘ └───────────┘ └──────┘ └─────────┘ │ runs Surefire plugin outputs target/surefire-reports/ mvn install = package + copy to ~/.m2 mvn deploy = install + push to Nexus/Artifactory mvn clean install = clean target/ + then install KEY RULE: Running phase N runs ALL phases 1 through N first. ══════════════════════════════════════════════════════════════
5Dependency Management
Version Conflict Resolution

When two dependencies pull in different versions of the same library, Maven uses nearest-wins strategy — the version closest to your project in the dependency tree wins.

Dependency Conflict DebuggingBASH
# Show full dependency tree with conflict markers mvn dependency:tree # Show only a specific dependency's transitive chain mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind # Analyse dependency conflicts mvn dependency:analyze # Force a specific version — put in <dependencyManagement> # This overrides transitive versions without adding a direct dependency
dependencyManagement — Force VersionsXML
<!-- In parent POM: declare versions WITHOUT adding dependencies --> <dependencyManagement> <dependencies> <dependency> <groupId>com.fasterxml.jackson.core</groupId> <artifactId>jackson-databind</artifactId> <version>2.15.3</version> </dependency> </dependencies> </dependencyManagement> <!-- In child POM: use without specifying version --> <dependencies> <dependency> <groupId>com.fasterxml.jackson.core</groupId> <artifactId>jackson-databind</artifactId> <!-- Version inherited from parent's dependencyManagement --> </dependency> </dependencies>
⚡ dependencyManagement declares versions without pulling in the dependency. Child modules inherit the version but must still declare the dependency to use it. This is the standard pattern in enterprise multi-module POMs.
Exclusions — Block Transitive Dependencies
Exclude Unwanted Transitive DependencyXML
<!-- Spring Boot brings in Logback; exclude to use Log4j2 instead --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-web</artifactId> <exclusions> <exclusion> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-logging</artifactId> </exclusion> </exclusions> </dependency>
6Plugins & Goals

Maven itself does almost nothing — everything is done by plugins. A goal is a specific task a plugin performs. A phase binds to one or more plugin goals.

Plugin Key Goals Use Case
maven-compiler-plugin compile, testCompile Compile Java source — set Java version here
maven-surefire-plugin test Run JUnit/TestNG unit tests
maven-failsafe-plugin integration-test, verify Run integration tests (separate from unit)
maven-jar-plugin jar Package into JAR; set main class in manifest
spring-boot-maven-plugin repackage, run Fat JAR with embedded Tomcat
jacoco-maven-plugin prepare-agent, report, check Code coverage — fail build if below threshold
maven-checkstyle-plugin check Enforce code style rules
spotbugs-maven-plugin check Static analysis for common bugs
maven-release-plugin prepare, perform Release workflow: tag, version bump, deploy
dockerfile-maven-plugin build, push Build Docker image from Maven
maven-compiler-plugin — Set Java VersionXML
<build> <plugins> <plugin> <groupId>org.apache.maven.plugins</groupId> <artifactId>maven-compiler-plugin</artifactId> <version>3.11.0</version> <configuration> <source>17</source> <target>17</target> <encoding>UTF-8</encoding> <parameters>true</parameters> <!-- Preserve method param names --> </configuration> </plugin> <!-- JaCoCo: fail build if coverage < 80% --> <plugin> <groupId>org.jacoco</groupId> <artifactId>jacoco-maven-plugin</artifactId> <version>0.8.11</version> <executions> <execution><goals><goal>prepare-agent</goal></goals></execution> <execution> <id>jacoco-check</id> <goals><goal>check</goal></goals> <configuration> <rules> <rule> <limits> <limit> <counter>LINE</counter> <minimum>0.80</minimum> <!-- 80% coverage required --> </limit> </limits> </rule> </rules> </configuration> </execution> </executions> </plugin> </plugins> </build>
7Repositories

Maven resolves dependencies from repositories in this order: local cache → company Nexus/Artifactory → Maven Central. In enterprise environments, everything goes through Nexus — internet access is blocked.

Configure Nexus in settings.xmlXML
<!-- ~/.m2/settings.xml — machine-level Maven config --> <settings> <mirrors> <!-- Route ALL Maven Central requests through company Nexus --> <mirror> <id>nexus</id> <mirrorOf>*</mirrorOf> <!-- * = intercept ALL repos --> <url>http://nexus.company.com:8081/repository/maven-public/</url> </mirror> </mirrors> <servers> <!-- Credentials for Nexus (never hardcode in pom.xml) --> <server> <id>nexus</id> <username>deploy-user</username> <password>${env.NEXUS_PASSWORD}</password> <!-- env var --> </server> </servers> </settings>
⚡ Never store Nexus passwords in pom.xml. Use environment variable interpolation in settings.xml, or Jenkins credential binding.
🏭 Production RealityIn Indian service company projects (Infosys, TCS, Wipro), your build will fail with "Could not resolve artifact" on day 1. Reason: corporate firewall blocks Maven Central. Solution: configure ~/.m2/settings.xml to point to the internal Nexus mirror. Ask your team lead for the Nexus URL before writing any code.

Profiles let you customise the build for different environments — dev, staging, production — without changing the pom.xml.

Environment ProfilesXML

9Multi-Module Projects

Real enterprise projects are multi-module: a parent POM coordinates shared configuration, and child modules inherit from it. This is the standard structure at Razorpay, PhonePe, and every large Spring Boot project.

Multi-Module Project LayoutTREE
payment-platform/ # Parent module ├── pom.xml # packaging: pom (not jar) ├── payment-api/ # REST API module │ └── pom.xml # inherits from parent ├── payment-domain/ # Business logic / entities │ └── pom.xml ├── payment-infra/ # DB, messaging, external clients │ └── pom.xml └── payment-service/ # Spring Boot entry point └── pom.xml
Parent POM — payment-platform/pom.xmlXML
<project> <groupId>com.company</groupId> <artifactId>payment-platform</artifactId> <version>2.0.0-SNAPSHOT</version> <packaging>pom</packaging> <!-- CRITICAL: parent must be 'pom' --> <!-- List all child modules --> <modules> <module>payment-domain</module> <module>payment-infra</module> <module>payment-api</module> <module>payment-service</module> </modules> <!-- Shared properties across ALL child modules --> <properties> <java.version>17</java.version> <spring-boot.version>3.2.0</spring-boot.version> </properties> </project>
Child POM — payment-api/pom.xmlXML
<project> <!-- Declare parent --> <parent> <groupId>com.company</groupId> <artifactId>payment-platform</artifactId> <version>2.0.0-SNAPSHOT</version> <relativePath>../pom.xml</relativePath> </parent> <artifactId>payment-api</artifactId> <!-- groupId and version inherited from parent --> <dependencies> <!-- Depend on sibling module --> <dependency> <groupId>com.company</groupId> <artifactId>payment-domain</artifactId> <version>${project.version}</version> </dependency> </dependencies> </project>
Build from Parent DirectoryBASH
# From payment-platform/ — builds ALL modules in dependency order mvn clean install # Build only specific module + its dependencies mvn clean install -pl payment-api -am # -pl = project list (modules to build) # -am = also make dependencies # -amd = also make dependents (reverse)

Skip Tests — When & How
Test Skip OptionsBASH
# Skip test EXECUTION (still compile) mvn package -DskipTests # Skip test compilation + execution mvn package -Dmaven.test.skip=true # Run only specific test class mvn test -Dtest=PaymentServiceTest # Run only specific method mvn test -Dtest=PaymentServiceTest#testPayment
⚠️ Warning-DskipTests vs -Dmaven.test.skip=true: the first still compiles tests. Use -DskipTests in dev; never in CI.
12CI/CD Integration
Maven in Jenkins Declarative PipelineGROOVY
pipeline { agent any tools { maven 'Maven-3.8.6' // name from Jenkins Global Tool Config jdk 'JDK-17' } stages { stage('Build') { steps { sh 'mvn clean compile' } } stage('Test') { steps { sh 'mvn test' } post { always { junit 'target/surefire-reports/*.xml' jacoco execPattern: 'target/jacoco.exec' } } } stage('Package') { steps { sh 'mvn package -DskipTests' archiveArtifacts artifacts: 'target/*.jar' } } stage('Deploy to Nexus') { when { branch 'main' } steps { sh 'mvn deploy -DskipTests -P production' } } } }
⚡ The tools block tells Jenkins which Maven/JDK installation to use. Configure these in Jenkins → Manage Jenkins → Global Tool Configuration before using them in pipelines.

name: Maven CI on: [push, pull_request] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-java@v4 with: java-version: '17' distribution: 'corretto' cache: 'maven' # Cache ~/.m2 between runs - name: Build and Test run: mvn clean verify - name: Upload Test Results uses: actions/upload-artifact@v4 if: always() with: name: test-results path: target/surefire-reports/

15Production Examples
Build Script for CI Pipeline
ci-build.sh — Production Maven Build ScriptBASH
#!/usr/bin/env bash set -euo pipefail # ── CI Build Script for Maven Projects ── BUILD_VERSION="${CI_BUILD_NUMBER:-local}" MAVEN_OPTS="${MAVEN_OPTS:--Xmx2048m -XX:+TieredCompilation}" log() { echo "[$(date '+%H:%M:%S')] $*"; } log "🔨 Starting build — version: ${BUILD_VERSION}" # Clean and validate mvn clean validate --batch-mode --no-transfer-progress # Run tests with code coverage log "🧪 Running tests..." mvn test \ --batch-mode \ --no-transfer-progress \ -Djacoco.destFile=target/jacoco.exec # Package (tests already ran) log "📦 Packaging..." mvn package -DskipTests \ --batch-mode \ --no-transfer-progress \ -Drevision="${BUILD_VERSION}" # Deploy to Nexus (main branch only) if [[ "${GIT_BRANCH:-}" == "main" ]]; then log "🚀 Deploying to Nexus..." mvn deploy -DskipTests --batch-mode --no-transfer-progress fi log "✅ Build complete: target/*.jar"
⚡ --batch-mode suppresses interactive prompts (essential in CI). --no-transfer-progress reduces noise in Jenkins logs. Always set these in CI pipelines.

21Interview Questions
Q1What is the difference between mvn install and mvn deploy?
install copies the artifact to your local ~/.m2/repository — only you can use it. deploy first does install, then pushes to the remote repository (Nexus/Artifactory) — the entire team can use it. In CI, you run deploy on main/release branches; install on feature branches.
Q2What is a SNAPSHOT version and when do you use it?
A SNAPSHOT (e.g., 1.0.0-SNAPSHOT) is an in-development version. Maven re-downloads SNAPSHOT dependencies periodically because they change. A release version (e.g., 1.0.0) is immutable — Maven caches it forever. Rule: develop with SNAPSHOTs, release with fixed versions. Never deploy a SNAPSHOT to production.
Q3What does mvn clean install -U do?
clean deletes target/. install builds and caches locally. -U (update snapshots) forces Maven to check remote repos for newer SNAPSHOT versions, bypassing the local cache. Use when a teammate published a new SNAPSHOT and your local cache is stale. Never use in CI where you want deterministic builds from the cache.
Q4Maven build fails with "Could not resolve artifact." What are the top 3 causes?
1. Network/firewall: corporate VPN blocks Maven Central. Fix: configure Nexus mirror in settings.xml. 2. Corrupted cache: partial download left a broken JAR in ~/.m2. Fix: delete the specific artifact directory and rebuild with -U. 3. Wrong repository: artifact lives in a non-standard repo not configured in your pom.xml or settings.xml. Fix: add the repository declaration.
Q5What is the difference between dependencies and dependencyManagement?
dependencies directly adds a dependency to the project. dependencyManagement only declares the version — it does not add the dependency. Child modules inherit the version from dependencyManagement but must still declare the dependency themselves. This lets the parent control all versions centrally without forcing every child to use every dependency.
22Interview Mode — Scenario Simulation

🎤 Senior DevOps Interview — Maven Round

You just joined a team whose Jenkins CI is randomly failing with "BUILD SUCCESS" on the test stage but tests are clearly not running. The test reports in Jenkins are empty. You have 10 minutes to diagnose it.
Q: Walk me through your diagnostic process.
Model Answer: First check the target/surefire-reports/ directory — if empty, Surefire is skipping tests, not running them. Then check if -DskipTests is set in the Jenkins job config or Jenkinsfile. Check Surefire plugin version — older versions miss JUnit 5 tests unless you add the JUnit 5 engine dependency. Finally check if test class names match Surefire's default patterns (**/*Test.java). If tests are named PaymentSpec.java, Surefire won't find them.
Q: The Spring Boot app builds fine locally but fails in Jenkins with NoClassDefFoundError. What's your hypothesis?
Model Answer: Different Java versions between local and Jenkins. Check java -version locally vs sh 'java -version' in Jenkinsfile. Or: a dependency with provided scope is missing at runtime because Jenkins doesn't have the expected application server. Or: the build uses a local JAR installed via mvn install locally but not present in the Jenkins workspace or Nexus.
23Common Mistakes
❌ Mistake 1 — Committing target/ to GitThe target/ directory contains build artifacts and .class files — hundreds of MB. Always add target/ to .gitignore. Verify with git ls-files target/ — should return empty.
❌ Mistake 2 — Storing Nexus Password in pom.xmlNever put credentials in pom.xml — it gets committed to Git. Use ~/.m2/settings.xml for credentials, and reference environment variables: ${env.NEXUS_PASSWORD}.
❌ Mistake 3 — Using SNAPSHOT in ProductionSNAPSHOT versions are re-downloaded whenever Maven finds a newer one. In production, every deploy could use a different binary. Always release with fixed versions (e.g., 1.2.3 not 1.2.3-SNAPSHOT).
❌ Mistake 4 — Skipping Tests in CI-DskipTests in your CI pipeline defeats the purpose of CI. Tests should always run in CI. Use it only in local dev builds when iterating on non-test code. The PR should never merge if CI runs with -DskipTests.
❌ Mistake 5 — Wrong packaging in Parent POMA parent (aggregator) POM must have <packaging>pom</packaging>. If you leave it as the default jar, Maven tries to produce a JAR from a POM-only project and fails with strange errors.
24Best Practices
✅ Centralise Versions in PropertiesDefine all dependency versions in <properties>, reference them as ${spring.version}. Never hardcode versions inside <dependency> tags directly. This makes upgrades a one-line change.
✅ Use --batch-mode in CIAlways run Maven with --batch-mode in CI pipelines. It suppresses interactive prompts and download progress bars, keeping Jenkins logs clean and parseable.
✅ Separate Unit and Integration TestsUse Surefire for unit tests (*Test.java) and Failsafe for integration tests (*IT.java). Integration tests run during the verify phase, not test — so you can skip them with mvn test for fast feedback loops.
✅ Pin Plugin VersionsAlways explicitly declare plugin versions in your POM. If you don't, Maven uses whatever's latest in Central — and that changes. Pin it: <version>3.11.0</version>. This is a CI determinism issue, not a style preference.
✅ Run mvn dependency:analyze in PRsThis catches: (a) declared but unused dependencies bloating your artifact, (b) used but undeclared dependencies that work only because a transitive dep brings them — these break when you upgrade.

27Summary & Key Takeaways
  • Maven coordinates (groupId:artifactId:version) uniquely identify every artifact — these are your build addresses
  • The 3 lifecycles are: default (compile → deploy), clean (delete target/), site (docs). Running a phase runs all prior phases automatically.
  • mvn package runs tests; mvn package -DskipTests skips them. Never skip tests in CI.
  • dependencyManagement declares versions in parent; child modules declare which they want — not both
  • SNAPSHOT versions are for development; release versions are for deployment. Never ship SNAPSHOTs.
  • Dependency scopes control classpath visibility: compile goes in JAR, test does not, provided is assumed to exist at runtime
  • Multi-module: parent POM has <packaging>pom</packaging>; children declare <parent>; reactor builds in dependency order
  • Never commit passwords to pom.xml; use settings.xml with environment variables for Nexus credentials
  • mvn dependency:tree and dependency:analyze are your diagnostic lifelines for build failures
  • Always use --batch-mode in CI; always pin plugin versions for reproducible builds
