Advanced Workloads

Beyond standard stateless Deployments, Kubernetes provides controllers for specific edge cases.

StatefulSets

Used for databases (like MySQL or Cassandra). They guarantee strict ordering and unique network identities (e.g., mysql-0, mysql-1) and ensure that each Pod gets its own dedicated PersistentVolumeClaim that survives Pod deletion.

statefulset.yaml 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 1Gi
DaemonSets

Ensures that exactly one copy of a Pod runs on every single worker node in the cluster. Commonly used for log collection (Fluentd, Promtail) or monitoring agents (Datadog).

Terminal 
kubectl get daemonset -n kube-system

ConfigMaps & Secrets

Decouple configuration artifacts from image content to keep containerized applications portable.

ConfigMaps

Store non-confidential data in key-value pairs (e.g., nginx.conf, application.properties).

Terminal 
kubectl create configmap app-config --from-literal=LOG_LEVEL=DEBUG

Secrets

Store confidential data (passwords, TLS certificates). Remember: Kubernetes Secrets are Base64 encoded, NOT encrypted by default! In production, integrate with AWS Secrets Manager or HashiCorp Vault.

Terminal 
kubectl create secret generic db-pass --from-literal=password=supersecret

Autoscaling (HPA & VPA)

Resource Requests & Limits

Before you can autoscale, you must define CPU and Memory boundaries for your Pods.

  • Requests: The minimum resources guaranteed to the Pod. Used by the scheduler to find a node with enough space.
  • Limits: The absolute maximum. If a container exceeds its Memory Limit, it is OOMKilled (Out Of Memory).
Horizontal Pod Autoscaler (HPA)

Scales the number of Pod replicas up or down based on observed CPU/Memory utilization.

Terminal 
kubectl autoscale deployment my-app --cpu-percent=70 --min=2 --max=10
Vertical Pod Autoscaler (VPA)

Automatically adjusts the CPU and Memory requests/limits of existing Pods (requires pod restart) if it notices they are starving for resources or over-provisioned.

Security: RBAC

Role-Based Access Control determines who can do what inside the cluster.

  • Role: Defines permissions (e.g., "can get/list pods") within a specific namespace.
  • ClusterRole: Same as Role, but cluster-wide (e.g., "can list nodes").
  • RoleBinding: Attaches a Role to a User, Group, or ServiceAccount.
  • ServiceAccount: The identity assigned to a Pod, allowing the Pod itself to securely talk to the Kubernetes API.
Terminal 
kubectl create role pod-reader --verb=get,list,watch --resource=pods
kubectl create rolebinding read-pods --role=pod-reader --user=jane

Network Policies

By default, all pods in Kubernetes can talk to all other pods. This is a massive security risk in a multi-tenant cluster.

Default Deny

A NetworkPolicy acts as a firewall. You can create a "Default Deny" policy that blocks all ingress traffic, and then explicitly allow traffic only from specific namespaces or pods using label selectors.

net-policy.yaml 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080

Istio Service Mesh

A Service Mesh intercepts all network traffic between your microservices by injecting a "sidecar" proxy (Envoy) into every Pod.

Why use Istio?

  1. mTLS (Mutual TLS): Automatically encrypts all traffic between pods without changing any application code.
  2. Traffic Management: Canary deployments (send 5% of traffic to v2, 95% to v1), retries, and circuit breakers.
  3. Observability: Generates beautiful traces and service topology maps in tools like Kiali and Jaeger.
Terminal 
# Inject Istio sidecars into the default namespace automatically
kubectl label namespace default istio-injection=enabled

GitOps with ArgoCD

Stop running kubectl apply manually! GitOps is the philosophy that your Git repository should be the single source of truth for your cluster's desired state.

How ArgoCD works
  • You install the ArgoCD controller inside your Kubernetes cluster.
  • You point ArgoCD to your GitHub repository containing your YAML or Helm charts.
  • ArgoCD continuously monitors the repo. If you merge a pull request changing an image tag to v2, ArgoCD instantly detects the drift and automatically pulls the changes into the cluster!
Terminal 
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
