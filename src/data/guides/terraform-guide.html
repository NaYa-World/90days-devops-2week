Infrastructure as Code with Terraform

Learn Terraform from absolute zero. No prior IaC experience needed. Build real AWS infrastructure using simple, human-readable configuration files.

1

What is Terraform?

💡 Real-World Analogy

Imagine you're ordering food. The imperative way is: "Go to the kitchen, boil water, add pasta, strain it, add sauce..." — you describe every single step. The declarative way (Terraform) is: "I want a plate of pasta bolognese." You describe what you want, and Terraform figures out all the steps to make it happen.

Terraform is a free, open-source tool by HashiCorp that lets you define cloud infrastructure (servers, databases, networks) in simple text files. Instead of clicking around the AWS Console, you write a file that says "I want an EC2 instance" and Terraform creates it for you.

Why should you learn Terraform?

  • Reproducible: Run the same file 100 times and get the same infrastructure. No more "it works on my account" problems.
  • Version Controlled: Store your infrastructure in Git, just like application code. Review changes in PRs before applying them.
  • Automated: No more clicking through the AWS console. One command creates everything.
  • Multi-Cloud: Works with AWS, Azure, GCP, Kubernetes, and 3000+ other providers.
Key Terms for Beginners:
Provider = The cloud platform you want to use (AWS, Azure, GCP).
Resource = A thing you want to create (EC2 instance, S3 bucket, VPC).
State = Terraform's memory. It remembers what it created so it can update or delete it later.
HCL = HashiCorp Configuration Language. The simple language Terraform files are written in.

Installing Terraform

Before you can use Terraform, you need to install it on your machine and configure AWS credentials.

Step 1: Install Terraform CLI

macOS (Homebrew)
brew tap hashicorp/tap
brew install hashicorp/tap/terraform
Ubuntu/Debian
sudo apt-get update && sudo apt-get install -y gnupg software-properties-common
wget -O- https://apt.releases.hashicorp.com/gpg | \
  gpg --dearmor | \
  sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg > /dev/null
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
  https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt-get update && sudo apt-get install terraform
Verify installation
terraform -version

Step 2: Configure AWS Credentials

Terraform needs your AWS Access Key and Secret Key to talk to AWS on your behalf.

Configure AWS CLI
aws configure
# It will ask for:
# AWS Access Key ID:     YOUR_ACCESS_KEY
# AWS Secret Access Key: YOUR_SECRET_KEY
# Default region name:   us-east-1
# Default output format: json
⚠️ Security Warning: Never hardcode AWS keys in your Terraform files! Always use aws configure or environment variables. Terraform automatically picks up credentials from ~/.aws/credentials.

The Core Workflow (Write → Plan → Apply)

💡 Real-World Analogy

Think of building a house. terraform init = hiring the construction crew. terraform plan = reviewing the blueprint before building. terraform apply = actually building the house. terraform destroy = demolishing the house.

The 4 Essential Commands

Command What it does
terraform init Initializes the project. Downloads the AWS provider plugin. Run this once when you start a new project or add a new provider.
terraform plan Shows you a preview of what will be created/changed/destroyed. Always run this before apply! It's your safety net.
terraform apply Actually creates/updates the infrastructure. It will show the plan first and ask you to type yes to confirm.
terraform destroy Deletes everything that Terraform created. Use with caution! It will ask for confirmation.

Your First Terraform Project (Step-by-Step)

Terminal — Follow these steps in order
# Step 1: Create a new project folder
mkdir my-first-terraform && cd my-first-terraform

# Step 2: Create your first .tf file (we'll write the content next)
touch main.tf

# Step 3: Initialize the project (downloads AWS provider)
terraform init

# Step 4: Preview what will happen
terraform plan

# Step 5: Create the infrastructure (type 'yes' when asked)
terraform apply

# Step 6: When done, clean up to avoid AWS charges!
terraform destroy

HCL Syntax Deep Dive

Terraform files use HCL (HashiCorp Configuration Language). It's designed to be easy to read, even for beginners. Every .tf file in your project directory is automatically loaded by Terraform.

The Anatomy of a Terraform File

hcl — main.tf (fully annotated)
# ─── STEP 1: Tell Terraform WHICH cloud to use ─────────────────
# The "provider" block connects Terraform to AWS.
# It uses your credentials from `aws configure`.
provider "aws" {
  region = "us-east-1"   # Which AWS data center region
}

# ─── STEP 2: Define WHAT you want to create ─────────────────────
# Syntax: resource "PROVIDER_TYPE" "YOUR_LOCAL_NAME" { ... }
#
#   "aws_instance" = AWS EC2 Instance (the resource type)
#   "web_server"   = A name YOU choose (used to reference it)
resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0"   # Amazon Machine Image (OS template)
  instance_type = "t2.micro"               # Size of the server (Free Tier)

  # Tags are labels. They don't affect the server, but help you
  # identify resources in the AWS Console.
  tags = {
    Name        = "MyFirstTerraformEC2"
    Environment = "dev"
  }
}

Common Terraform File Structure

You can put everything in one file, but the convention is to split it into multiple files for clarity:

File Purpose
main.tf Your primary resources (EC2, VPC, S3, etc.)
variables.tf Input variables (like function parameters)
outputs.tf Values to display after apply (like the server's IP)
providers.tf Provider configuration (AWS region, version constraints)
backend.tf Where to store the state file (S3, local, etc.)
terraform.tfvars Actual values for your variables (like a .env file)

Variables & Outputs

💡 Real-World Analogy

Variables are like the blanks in a Mad Libs game. You define the blank ("I want a server of size ____"), and then fill it in later. This lets you reuse the same Terraform config for dev, staging, and prod by just changing the variables.

Defining Variables

hcl — variables.tf
# A simple variable with a default value
variable "instance_type" {
  description = "The size of the EC2 instance"
  type        = string
  default     = "t2.micro"   # If no value provided, use this
}

# A variable WITHOUT a default — Terraform will ASK you for it
variable "environment" {
  description = "The deployment environment (dev, staging, prod)"
  type        = string
}

# A number variable
variable "server_count" {
  description = "How many servers to create"
  type        = number
  default     = 1
}

Using Variables in Resources

hcl — main.tf
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = var.instance_type    # ← Use the variable!

  tags = {
    Name = "web-${var.environment}"   # ← String interpolation
  }
}

Setting Variable Values

hcl — terraform.tfvars
# This file automatically loads when you run terraform apply
instance_type = "t3.small"
environment   = "dev"
server_count  = 2

Defining Outputs

Outputs display useful info after terraform apply finishes (like the public IP of your new server).

hcl — outputs.tf
output "server_public_ip" {
  description = "The public IP of the web server"
  value       = aws_instance.web.public_ip
}

output "server_id" {
  description = "The EC2 instance ID"
  value       = aws_instance.web.id
}

What is Terraform State?

💡 Real-World Analogy

Think of the state file as a shopping list with checkmarks. When you run terraform apply, Terraform checks each item on the list. If an item is already checked (already exists in AWS), it skips it. If it's new, it creates it. If you remove an item from the list, Terraform deletes it from AWS.

After you run terraform apply, Terraform creates a file called terraform.tfstate. This JSON file maps your .tf configuration to real-world AWS resources. Without it, Terraform wouldn't know what it already created.

🚨 NEVER do these things to the state file:
• Never delete it (Terraform loses track of your resources — they become "orphaned" in AWS)
• Never edit it manually (use terraform state commands instead)
• Never commit terraform.tfstate to Git (it may contain secrets!)

Remote State (AWS S3)

By default, the state file is saved locally on your laptop. This is fine for learning, but in a team, everyone needs to share the same state. The solution? Store it in an S3 bucket.

Step 1: Create the S3 bucket first (one-time setup)

Terminal
aws s3api create-bucket \
  --bucket my-terraform-state-bucket-12345 \
  --region us-east-1

Step 2: Configure Terraform to use it

hcl — backend.tf
terraform {
  backend "s3" {
    bucket = "my-terraform-state-bucket-12345"
    key    = "project-name/terraform.tfstate"
    region = "us-east-1"
  }
}
✅ After adding a backend: Run terraform init again. Terraform will detect the new backend and ask if you want to migrate your local state to S3. Type yes.

State Locking (DynamoDB)

💡 Real-World Analogy

Imagine two people editing the same Google Doc at the same time — changes can conflict. State locking is like adding a "🔒 Editing…" banner. While one person is running terraform apply, nobody else can run it until the first person finishes.

Step 1: Create the DynamoDB table

Terminal
aws dynamodb create-table \
  --table-name terraform-locks \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST

Step 2: Add locking to your backend

hcl — backend.tf (complete)
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket-12345"
    key            = "project-name/terraform.tfstate"
    region         = "us-east-1"
    
    # State Locking — prevents two people from running apply at once
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

Modules (Reusable Code)

💡 Real-World Analogy

A module is like a Lego set with instructions. Once you build the first set (e.g., a VPC module), you can stamp out copies for dev, staging, and prod just by calling it multiple times with different inputs.

Modules let you package a group of resources together and reuse them. Instead of copy-pasting 200 lines of VPC code, you create a module once, then call it.

Calling a Module

hcl — main.tf
# Use a local module stored in ./modules/web-server/
module "web_cluster" {
  source        = "./modules/web-server"
  
  # Pass variables to the module
  cluster_name  = "production"
  instance_type = "t3.medium"
  min_size      = 2
  max_size      = 10
}

# You can also use modules from the Terraform Registry
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"
  
  name    = "my-vpc"
  cidr    = "10.0.0.0/16"
}

Workspaces (Multi-Environment)

Workspaces allow you to manage multiple environments (dev, staging, prod) using the exact same Terraform files. Each workspace gets its own isolated state file.

Workspace Commands

Terminal
# List all workspaces (* marks the active one)
terraform workspace list

# Create a new workspace
terraform workspace new dev

# Switch to a different workspace
terraform workspace select prod

# Show current workspace
terraform workspace show

Using Workspaces in Code

hcl — main.tf
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  # Use a bigger server in prod, smaller in dev
  instance_type = terraform.workspace == "prod" ? "t3.large" : "t2.micro"

  tags = {
    Name        = "web-${terraform.workspace}"
    Environment = terraform.workspace
  }
}
L1

Beginner: EC2 & Security Group

Your first Terraform project. Provision a web server and open port 80 to the internet.

hcl — main.tf
provider "aws" {
  region = "us-east-1"
}

resource "aws_security_group" "web_sg" {
  name        = "allow_http"
  description = "Allow HTTP inbound traffic"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami                    = "ami-0c55b159cbfafe1f0"
  instance_type          = "t2.micro"
  vpc_security_group_ids = [aws_security_group.web_sg.id]

  tags = {
    Name = "L1-WebServer"
  }
}

output "public_ip" {
  value = aws_instance.web.public_ip
}
✅ After apply: Run terraform output public_ip to get the IP. Open it in your browser (http://IP) — you should see a connection, proving the security group works! Don't forget to run terraform destroy when done.

Intermediate: Custom VPC Architecture

Provision the networking foundation for EKS or ECS. Create a VPC with public subnets, an Internet Gateway, and Route Tables.

hcl — network.tf
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "L2-VPC" }
}

resource "aws_subnet" "public_a" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = true
  availability_zone       = "us-east-1a"
  tags = { Name = "public-subnet-a" }
}

resource "aws_subnet" "public_b" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.2.0/24"
  map_public_ip_on_launch = true
  availability_zone       = "us-east-1b"
  tags = { Name = "public-subnet-b" }
}

resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id
  tags = { Name = "L2-IGW" }
}

resource "aws_route_table" "public_rt" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }
  tags = { Name = "public-route-table" }
}

# Associate subnets with the route table
resource "aws_route_table_association" "a" {
  subnet_id      = aws_subnet.public_a.id
  route_table_id = aws_route_table.public_rt.id
}

resource "aws_route_table_association" "b" {
  subnet_id      = aws_subnet.public_b.id
  route_table_id = aws_route_table.public_rt.id
}

Advanced: S3 + CloudFront Static Site Module

Create a highly available, globally distributed static website using Terraform Modules.

  • Create a reusable module in a /modules/static-site directory.
  • Provision an S3 bucket configured for static web hosting.

Troubleshooting Guide

❌ Error: No valid credential sources found

Terraform cannot find your AWS credentials.

Fix
# Option 1: Configure via AWS CLI
aws configure

# Option 2: Export as environment variables
export AWS_ACCESS_KEY_ID="your-key"
export AWS_SECRET_ACCESS_KEY="your-secret"
export AWS_REGION="us-east-1"

# Verify it works
aws sts get-caller-identity

❌ Error: Failed to load plugin / Provider not found

The required provider plugin hasn't been downloaded.

Fix
# Re-initialize and download providers
terraform init

# If still failing, clear the cache and retry
rm -rf .terraform .terraform.lock.hcl
terraform init

❌ Error: Error acquiring the state lock

Someone else is running terraform apply, or a previous run crashed and left a stale lock.

Fix
# CAUTION: Only do this if you are SURE nobody else is running apply!
terraform force-unlock LOCK_ID

# The LOCK_ID is shown in the error message.
# Example: terraform force-unlock a1b2c3d4-e5f6-7890-abcd-ef1234567890

❌ Error: Resource already exists

The resource exists in AWS but Terraform doesn't know about it (it's not in the state file).

Fix
# Import the existing resource into Terraform state
terraform import aws_instance.web i-0abc123def456789

# After importing, run plan to verify
terraform plan

❌ Error: Cycle detected in resource dependencies

Resource A depends on B, and B depends on A — creating an infinite loop.

Fix
# Visualize the dependency graph to find the cycle
terraform graph | dot -Tpng > graph.png

# Then refactor your code to break the circular dependency.
# Common fix: Use "depends_on" only where truly needed,
# and avoid referencing resource attributes in a loop.

❌ Error: Backend config changed — reinitialize

You modified the backend block (e.g., changed the S3 bucket name).

Fix
# Re-initialize with the -reconfigure flag
terraform init -reconfigure

# Or if you want to migrate the old state to the new backend:
terraform init -migrate-state

❌ terraform destroy is stuck / taking forever

Some resources (like RDS, EKS, or NAT Gateways) take 10–20 minutes to delete. If it's truly stuck:

Fix
# Target a specific resource to destroy first
terraform destroy -target=aws_nat_gateway.main

# If Terraform is unresponsive, Ctrl+C to cancel, then
# manually delete the resource in the AWS Console and
# remove it from state:
terraform state rm aws_nat_gateway.main

⚠️ Common Gotchas for Beginners

  • Forgot to run terraform init — always run init in a new directory or after adding a provider.
  • Wrong region — if you can't find your resources in the Console, check you're looking in the right region.
  • AMI IDs are region-specific — an AMI that works in us-east-1 won't work in eu-west-1.
  • Free Tier limits — t2.micro is free for 750 hrs/month. Using t3.large will cost money!
  • Forgot terraform destroy — you WILL be charged for running resources. Always destroy after practice.
  • State file in Git — add *.tfstate and .terraform/ to your .gitignore.
