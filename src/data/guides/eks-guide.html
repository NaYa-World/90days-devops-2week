Amazon Elastic Kubernetes Service

Create Your First EKS Cluster

A beginner-friendly, step-by-step guide that explains what you do and why you do it — so you actually understand Kubernetes on AWS.

🤔 Wait — What Even IS EKS?

Kubernetes (K8s) is an open-source system that automatically manages your Docker containers — starting them, restarting them if they crash, scaling them up when traffic increases, and balancing traffic across them.

Amazon EKS (Elastic Kubernetes Service) is AWS's managed Kubernetes. It means AWS runs the "brain" of Kubernetes for you (the control plane), so you don't have to install, patch, or babysit it yourself.

Think of it like this:

🍳 Restaurant Analogy

• Head Chef = Control Plane (decides what gets cooked)

• Kitchen Staff = Worker Nodes (actually cook the food)

• Recipes = YAML Manifests (instructions for what to make)

• Dishes = Pods (the running containers)

⚙️ In Kubernetes Terms

• Control Plane = API Server + Scheduler + etcd (AWS manages this)

• Worker Nodes = EC2 instances running your containers

• Deployment = "Run 3 copies of this app, always"

• Service = A stable URL/IP for your pods

In short: EKS lets you run containerized apps at scale without managing Kubernetes infrastructure yourself. You focus on your app — AWS handles the rest.

⚙️ How Everything Connects
💻

1. Your Laptop (Jumpbox)

You install awscli, kubectl, and eksctl. This is your command center.

🔒

2. AWS IAM

Your laptop authenticates to AWS using your Access Keys (Identity & Access Management).

🌐

3. EKS Control Plane

eksctl tells AWS to create the EKS Master Node and a secure VPC network.

🖥️

4. Worker Nodes (EC2)

EC2 instances are launched in your VPC and attached to the EKS Control Plane.

📦

5. Your Application (Pods)

You use kubectl to deploy containers (Pods) onto those Worker Nodes!

🎯 Choose Your Path

There are two ways to create an EKS cluster. Pick the one that matches your comfort level:

✅ RECOMMENDED FOR BEGINNERS
🚀 Easy Path (eksctl)
1 command creates everything — VPC, IAM roles, cluster, and nodes. Just do Steps 1 → 4 → 6 → 7. Skip Steps 2, 3, 5.
LEARN THE INTERNALS
🔧 Manual Path (Console UI)
Step-by-step in AWS Console — Create IAM roles, VPC, cluster, and nodes individually. More clicks, but you'll understand every piece.

Install Prerequisites

⏱ ~15 min

Before touching AWS, you need CLI tools on your local machine. Think of them as your toolkit.

🍺 1a — Install Homebrew (macOS only)

All Mac install commands below use Homebrew — the package manager for macOS. If you don't have it yet:

bash — macOS Terminal
# Check if Homebrew is already installed
brew --version

# If "command not found", install Homebrew with this one-liner:
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# After install, follow the instructions it prints to add brew to your PATH.
# Usually something like:
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
eval "$(/opt/homebrew/bin/brew shellenv)"

# Verify Homebrew works
brew --version
✅ Success: You see Homebrew 4.x.x
💎 What is Homebrew?

Homebrew is like an app store for your terminal. Instead of downloading installers from websites, you just type brew install <tool> and it handles everything — download, install, and PATH setup. Linux users don't need Homebrew (use apt or curl instead).

🔧 1b — Install AWS CLI

The AWS CLI lets you interact with AWS from your terminal.

bash

aws --version
✅ Success: You see something like aws-cli/2.x.x

kubectl is the Kubernetes CLI. You'll use it to deploy apps and manage your cluster.

bash

🔑 1e — Get Your AWS Access Keys (Console UI)

You need an Access Key ID and Secret Access Key to link the CLI to your AWS account. Here's how to get them:

🔗 https://console.aws.amazon.com/iam/

  1. Log in to the AWS Management Console at console.aws.amazon.com.
  2. In the top search bar, type IAM and click on IAM from the results.
  3. In the left sidebar, click Users.
  4. Click Create user (orange button, top-right).
    • User name: enter eks-admin
    • Check "Provide user access to the AWS Management Console" if you want console login too.
    • Click Next.
  5. On Set permissions:
    • Select "Attach policies directly".
    • Search and check AdministratorAccess (for learning only!).
    • Click Next → Create user.
  6. Click your new user name (eks-admin) to open the details.
  7. Go to the "Security credentials" tab.
  8. Scroll to "Access keys" and click Create access key.
  9. Select "Command Line Interface (CLI)", check confirmation, click Next.
  10. Click Create access key. You'll see:
    • Access Key ID — e.g., AKIAIOSFODNN7EXAMPLE
    • Secret Access Key — e.g., wJalrXUtnFEMI/K7MDENG/bPxRfi...

    ⚠️ Copy BOTH values NOW and click "Download .csv"! The Secret Key is shown only once.
🔧 1f — Configure AWS Credentials (Method 1: aws configure)

The easiest way — paste your keys into the interactive prompt:

bash
aws configure
# Paste when prompted:
#   AWS Access Key ID:       AKIAIOSFODNN7EXAMPLE    (from Step 10 above)
#   AWS Secret Access Key:   wJalrXUtnFEMI/K7MD...  (from Step 10 above)
#   Default region:          us-east-1  (pick the region closest to you)
#   Default output format:   json

# Verify it works:
aws sts get-caller-identity
# Should show your Account ID, User ARN, and User ID
✅ Success: You see your Account ID and User ARN in the output
🔧 1g — Configure AWS Credentials (Method 2: Environment Variables)

Alternatively, you can set credentials as environment variables. This is useful when switching between multiple AWS accounts or in CI/CD pipelines:

bash — set for current terminal session
# Set your AWS credentials as environment variables
# Replace the values with YOUR actual keys from Step 1e
export AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
export AWS_DEFAULT_REGION=us-east-1

# Verify it works
aws sts get-caller-identity
⚠️ Important

The export commands above only last for your current terminal session. If you close the terminal, they're gone! To make them permanent, add them to your shell profile:

bash — make persistent on macOS (zsh)
# macOS uses zsh by default — add to ~/.zshrc
echo 'export AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE' >> ~/.zshrc
echo 'export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY' >> ~/.zshrc
echo 'export AWS_DEFAULT_REGION=us-east-1' >> ~/.zshrc

# Reload your shell config (or just open a new terminal)
source ~/.zshrc

# Verify it persists
aws sts get-caller-identity
echo $AWS_DEFAULT_REGION   # Should print: us-east-1
bash — make persistent on Linux (bash)
# Linux uses bash by default — add to ~/.bashrc
echo 'export AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE' >> ~/.bashrc
echo 'export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY' >> ~/.bashrc
echo 'export AWS_DEFAULT_REGION=us-east-1' >> ~/.bashrc

# Reload
source ~/.bashrc
💎 Which method should I use?

For beginners: Use Method 1 (aws configure) — it's simpler and stores keys in ~/.aws/credentials automatically.

For DevOps work: Use Method 2 (env vars) — it's the standard for CI/CD pipelines, Docker containers, and switching between multiple AWS accounts.

Priority order: If both are set, environment variables take priority over ~/.aws/credentials. This means you can override aws configure settings temporarily with export.

✅ Success: aws sts get-caller-identity works from any new terminal window
💡 Why this step?

Without these tools you literally cannot proceed. AWS CLI authenticates you, kubectl manages Kubernetes, and eksctl automates EKS provisioning. The Access Keys are like a username/password for the CLI — they prove to AWS who you are.

⚠️ Security Warning

Never commit your AWS credentials to Git. Use ~/.aws/credentials or environment variables only. For production, prefer IAM Identity Center (SSO).

Create IAM Roles Manual Path

⏱ ~10 min
💡 Easy Path Users

You can skip this step! eksctl creates IAM roles automatically. But reading through it helps you understand what's happening behind the scenes.

EKS needs two IAM Roles:

  • Cluster Role — Lets the EKS control plane manage AWS resources.
  • Node Role — Lets worker nodes pull images, assign IPs, and register with the cluster.
🔒 2a — Create the EKS Cluster Role (Console UI)

🔗 IAM Console → Roles

  1. Open the IAM Console. In the left sidebar, click Roles.
  2. Click Create role (top-right).
  3. On "Select trusted entity":
    • Choose "AWS service"
    • In "Use case", search and select EKS
    • Select "EKS - Cluster"
    • Click Next
  4. On "Add permissions", AmazonEKSClusterPolicy is pre-selected. Click Next.
  5. Role name: enter myEKSClusterRole → Click Create role.
  6. ✅ Green banner: "Role myEKSClusterRole created"
🔒 2b — Create the Node Group Role (Console UI)

🔗 IAM Console → Roles

  1. Click Roles → Create role again.
  2. Trusted entity: "AWS service" → Use case: EC2 → Click Next
  3. Search and check all three policies:

    AmazonEKSWorkerNodePolicy — Lets nodes register with the cluster
    AmazonEKS_CNI_Policy — Lets VPC CNI plugin assign pod IPs
    AmazonEC2ContainerRegistryReadOnly — Lets nodes pull Docker images from ECR

    💡 Search one at a time, check the box, clear search, repeat. Checked policies persist.

    Click Next.
  4. Role name: enter myEKSNodeRole → Verify 3 policies listed → Click Create role.
  5. ✅ Green banner: "Role myEKSNodeRole created"
💡 Why this step?

AWS follows the principle of least privilege. Nothing can do anything without explicit permission. The Cluster Role lets EKS manage networking and logging. The Node Role lets EC2 instances pull images and join the cluster. Without these roles, your cluster cannot start.

Set Up VPC & Networking Manual Path

⏱ ~10 min
💡 Easy Path Users

You can skip this step! eksctl creates the VPC automatically. But reading through it helps you understand networking.

A VPC (Virtual Private Cloud) is your isolated network in AWS. Your cluster lives inside it. You need public subnets (for load balancers) and private subnets (for worker nodes) across at least 2 Availability Zones.

🌐 3a — Create VPC via CloudFormation Console

🔗 CloudFormation Console

  1. Open the CloudFormation Console. Click Create stack → "With new resources (standard)".
  2. Under Specify template:
    • Select "Amazon S3 URL"
    • Paste this URL:
    https://s3.us-west-2.amazonaws.com/amazon-eks/cloudformation/2020-10-29/amazon-eks-vpc-private-subnets.yaml
    • Click Next
  3. Stack name: enter eks-vpc → Click Next
  4. Leave all defaults on "Configure stack options" → Click Next
  5. Review and click Submit. Wait ~2-3 minutes until status shows CREATE_COMPLETE.
  6. Click on your eks-vpc stack → Go to the "Outputs" tab.
    • Save these values! You'll need SubnetIds, SecurityGroups, and VpcId in the next step.
✅ Success: Stack status shows CREATE_COMPLETE and you can see the Outputs tab
💡 Why this step?

Kubernetes pods need a network to communicate. They get IP addresses from the VPC subnet range. Multiple AZs mean if one data center goes down, your app survives. Public/private subnet split keeps your nodes behind a NAT gateway (security best practice).

4

Create the EKS Cluster

⏱ ~15-20 min

This is the big one — creating the Kubernetes cluster itself.

🚀 One Command Does EVERYTHING

This single command creates the VPC, IAM roles, EKS cluster, and worker nodes — all at once. Just copy, paste, wait ~15 min:

bash
eksctl create cluster \
  --name my-first-cluster \
  --region us-east-1 \
  --version 1.30 \
  --nodegroup-name standard-workers \
  --node-type t3.medium \
  --nodes 2 \
  --nodes-min 1 \
  --nodes-max 3 \
  --managed

⏳ This takes ~15-20 minutes. Go grab a coffee. You'll see log output like:

output
[✓] EKS cluster "my-first-cluster" in "us-east-1" region is ready
[✓] created managed nodegroup "standard-workers"
[✓] kubectl configured for "my-first-cluster"
✅ Success: You see "EKS cluster is ready" — eksctl also auto-configures kubectl for you!
💡 What eksctl created for you

• A VPC with public + private subnets across 2 AZs
• IAM roles for the cluster and nodes
• The EKS control plane
• 2 worker nodes (t3.medium EC2 instances)
• Auto-configured your kubectl
That's why eksctl is amazing for beginners — all of this in one command!

🔧 4a — Create Cluster via EKS Console

🔗 EKS Console

  1. Open the EKS Console. Click Add cluster → Create.
  2. On "Configure cluster":
    • Name: my-first-cluster
    • Kubernetes version: 1.30 (latest stable)
    • Cluster service role: select myEKSClusterRole (created in Step 2)
    • Click Next
  3. On "Specify networking":
    • VPC: select the VPC created in Step 3 (look for the eks-vpc stack's VPC ID)
    • Subnets: select all subnets from your eks-vpc stack
    • Security groups: select the security group from your eks-vpc Outputs
    • Cluster endpoint access: select "Public and private"
    • Click Next
  4. On "Configure observability": leave defaults → Click Next
  5. On "Select add-ons": leave defaults (CoreDNS, kube-proxy, VPC CNI) → Click Next
  6. On "Configure selected add-ons settings": leave defaults → Click Next
  7. Review everything → Click Create.
  8. ⏳ Wait ~10-15 minutes until cluster status changes to Active.
✅ Success: Cluster status shows "Active" in the EKS Console
💡 Why this step?

This creates the Kubernetes control plane — the "brain" of your cluster. It includes the API server (where kubectl sends requests), etcd (the cluster database), the scheduler (decides which node runs your pod), and the controller manager. AWS manages ALL of this for you — you never SSH into a master node.

Add a Managed Node Group Manual Path

⏱ ~5 min
💡 Easy Path Users

You can skip this step! eksctl already created your nodes. But reading through it helps you understand node groups.

The control plane is running but has no workers. Now you add EC2 instances where your containers actually run.

🖥️ 5a — Add Nodes via EKS Console

🔗 EKS Console → Clusters

  1. Open the EKS Console. Click on your cluster name (my-first-cluster).
  2. Go to the "Compute" tab. Under "Node groups", click Add node group.
  3. On "Configure node group":
    • Name: standard-workers
    • Node IAM role: select myEKSNodeRole (created in Step 2)
    • Click Next
  4. On "Set compute and scaling":
    • Instance types: t3.medium (2 vCPU, 4 GB RAM)
    • Minimum size: 1
    • Maximum size: 3
    • Desired size: 2
    • Click Next
  5. On "Specify networking": leave the pre-selected subnets → Click Next
  6. Review → Click Create. Wait ~3-5 minutes until status shows Active.
✅ Success: Node group status shows "Active" and you see 2 nodes
💡 Why this step?

The control plane alone can't run your apps. It's like having a manager with no employees. Worker nodes are the EC2 instances where your containers actually execute. A managed node group means AWS handles OS patching, graceful draining during updates, and auto-scaling.

Configure kubectl

⏱ ~2 min
💡 Easy Path Note

eksctl already configured kubectl for you! Just run the verification command below to confirm.

Point your local kubectl at your new cluster:

bash
# Update kubeconfig (skip if you used eksctl — it did this already)
aws eks update-kubeconfig \
  --name my-first-cluster \
  --region us-east-1

# ✅ VERIFY — you should see your worker nodes listed as "Ready"
kubectl get nodes

# Expected output:
# NAME                             STATUS   ROLES    AGE   VERSION
# ip-192-168-xx-xx.ec2.internal    Ready    <none>   5m    v1.30.x
# ip-192-168-yy-yy.ec2.internal    Ready    <none>   5m    v1.30.x
✅ Success: You see 2 nodes with STATUS "Ready"
💡 Why this step?

kubectl uses ~/.kube/config to know where your cluster is. The update-kubeconfig command writes the API server endpoint and authentication config. After this, every kubectl command talks to your EKS cluster.

Deploy a Sample Application

⏱ ~5 min

Time to prove it works! You'll deploy Nginx and expose it to the internet.

📄 7a — Create the Deployment File

Save this as nginx-deployment.yaml (create the file in any folder):

yaml — nginx-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 2                  # Run 2 copies for availability
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "250m"
            memory: "256Mi"
🌐 7b — Create the Service File

Save this as nginx-service.yaml (same folder):

yaml — nginx-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: LoadBalancer         # Creates an AWS Load Balancer automatically
  selector:
    app: nginx
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
▶️ 7c — Deploy!
bash
# Deploy the app
kubectl apply -f nginx-deployment.yaml
kubectl apply -f nginx-service.yaml

# Watch pods come up (wait for STATUS = Running)
kubectl get pods -w

# Get the external URL (wait 1-2 min for AWS to assign it)
kubectl get service nginx-service

# Copy the EXTERNAL-IP and paste it in your browser!
# You should see the "Welcome to nginx!" page 🎉
✅ Success: You see "Welcome to nginx!" in your browser
💡 Why this step?

A Deployment tells Kubernetes "always run 2 copies of this container." If one crashes, K8s creates a replacement. The LoadBalancer Service tells AWS to create an ELB and route internet traffic to your pods. This deploy-then-expose pattern is how every Kubernetes app works.

Verify & Monitor

⏱ ~5 min

Essential commands you'll use every day:

bash — daily kubectl commands
# ──── Cluster Info ────
kubectl cluster-info                    # API server endpoint
kubectl get nodes -o wide               # Node details

# ──── Workload Status ────
kubectl get pods                        # Your pods
kubectl get pods -A                     # ALL pods (including system)
kubectl get deployments                 # Deployment status
kubectl get services                    # Service endpoints

# ──── Debugging (your #1 tools!) ────
kubectl describe pod <pod-name>         # Detailed info + events
kubectl logs <pod-name>                 # Container stdout/stderr
kubectl logs <pod-name> -f              # Stream logs live

# ──── Shell into a Container ────
kubectl exec -it <pod-name> -- /bin/sh  # Open shell inside container

# ──── Resource Usage ────
kubectl top nodes                       # CPU/Memory per node
kubectl top pods                        # CPU/Memory per pod
💡 Why this step?

Observability is everything. describe shows events (pull failures, crash loops). logs shows your app's output. top reveals resource usage. Master these now — they save hours of debugging later.

Day 1 Cheat Sheet (eksctl & kubectl)

Here are the core day-to-day commands you will need to manage your EKS cluster and nodes from your laptop.

💻 Cluster Management
bash
# Create cluster AND node group together (Easy Path)
eksctl create cluster --name my-cluster --region us-east-1 --nodegroup-name workers --node-type t3.medium --nodes 2

# Create ONLY the cluster (No worker nodes yet)
eksctl create cluster --name my-cluster --region us-east-1 --without-nodegroup

# Update your laptop's config to connect to the cluster
aws eks update-kubeconfig --region us-east-1 --name my-cluster

# Delete the entire cluster and all nodes
eksctl delete cluster --name my-cluster --region us-east-1
🖥️ Node Group Management (Scaling)
bash
# Add a NEW node group to an existing cluster
eksctl create nodegroup --cluster my-cluster --region us-east-1 --name more-workers --node-type t3.large --nodes 3

# Scale an existing node group up or down (e.g., change from 2 nodes to 5)
eksctl scale nodegroup --cluster my-cluster --name workers --nodes 5

# Delete a node group (removes those specific EC2 instances)
eksctl delete nodegroup --cluster my-cluster --name workers
📦 Application Deployment
bash
# See all running pods
kubectl get pods -A

# Deploy an app from a YAML file
kubectl apply -f my-app.yaml

# Delete that app
kubectl delete -f my-app.yaml
🔍 Troubleshooting Pods
bash
# Find out WHY a pod is crashing or stuck (e.g., "Insufficient CPU")
kubectl describe pod <pod-name>

# View the actual console logs from your application code
kubectl logs <pod-name>

# Stream logs live (like tail -f)
kubectl logs -f <pod-name>
📂 Namespaces (Where is my app?)

If kubectl get pods says "No resources found", you might be in the wrong namespace!

bash
# See all namespaces
kubectl get namespaces

# Get pods in a specific namespace
kubectl get pods -n <namespace-name>

# Get pods across ALL namespaces at once
kubectl get pods -A
🌐 Port Forwarding (Quick Testing)

Test your app locally before setting up complex Load Balancers.

bash
# Forward a local port (8080) to the service port (80)
kubectl port-forward svc/<service-name> 8080:80

# Now open your browser and go to: http://localhost:8080

🌱 Project 1 — Custom Portfolio Website (Easy)

New concepts: ConfigMap Volume Mounts Custom HTML

Instead of the default Nginx page, deploy your own website using a ConfigMap to inject custom HTML — no Docker image building required!

yaml — project1-portfolio.yaml
# ──── 1. ConfigMap: Your custom HTML page ────
apiVersion: v1
kind: ConfigMap
metadata:
  name: portfolio-html
data:
  index.html: |
    <!DOCTYPE html>
    <html>
    <head>
      <title>My Portfolio on EKS</title>
      <style>
        body { font-family: system-ui; background: #0f172a; color: #e2e8f0;
               display: flex; justify-content: center; align-items: center;
               min-height: 100vh; margin: 0; }
        .card { background: #1e293b; padding: 3rem; border-radius: 16px;
                text-align: center; max-width: 500px; box-shadow: 0 20px 60px rgba(0,0,0,.5); }
        h1 { color: #818cf8; margin-bottom: 0.5rem; }
        .badge { background: #10b981; color: #fff; padding: 4px 12px;
                 border-radius: 999px; font-size: 12px; font-weight: 700; }
        p { color: #94a3b8; line-height: 1.6; }
      </style>
    </head>
    <body>
      <div class="card">
        <span class="badge">Running on Kubernetes!</span>
        <h1>👋 Hi, I'm [Your Name]</h1>
        <p>This website is running on an Amazon EKS cluster
           with Kubernetes. I built this as part of my DevOps learning journey.</p>
        <p><strong>Pod:</strong> served by Nginx in a K8s pod</p>
      </div>
    </body>
    </html>
---
# ──── 2. Deployment: Nginx serves the ConfigMap HTML ────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: portfolio
spec:
  replicas: 2
  selector:
    matchLabels:
      app: portfolio
  template:
    metadata:
      labels:
        app: portfolio
    spec:
      containers:
      - name: nginx
        image: nginx:1.25-alpine
        ports:
        - containerPort: 80
        volumeMounts:            # Mount ConfigMap as a file
        - name: html-volume
          mountPath: /usr/share/nginx/html
        resources:
          requests:
            cpu: "50m"
            memory: "64Mi"
          limits:
            cpu: "100m"
            memory: "128Mi"
      volumes:                  # Define the ConfigMap as a volume
      - name: html-volume
        configMap:
          name: portfolio-html
---
# ──── 3. Service: Expose to the internet ────
apiVersion: v1
kind: Service
metadata:
  name: portfolio-service
spec:
  type: LoadBalancer
  selector:
    app: portfolio
  ports:
  - port: 80
    targetPort: 80

kubectl apply -f project1-portfolio.yaml

# Watch pods come up
kubectl get pods -l app=portfolio -w

# Get your website URL

🔥 Project 3 — Microservices with Auto-Scaling (Hard)

New concepts: Namespace Secret HPA (Auto-Scaling) Health Checks Resource Tuning

Deploy a production-style app with Namespaces for isolation, Secrets for passwords, Health checks for reliability, and Horizontal Pod Autoscaler to handle traffic spikes.

yaml — project3-microservices.yaml
# ──── 1. Namespace: Isolate this project ────
apiVersion: v1
kind: Namespace
metadata:
  name: production-app
---
# ──── 2. Secret: Store the Redis password ────
apiVersion: v1
kind: Secret
metadata:
  name: redis-secret
  namespace: production-app
type: Opaque
stringData:                   # K8s will base64-encode for you
  redis-password: "MyS3cur3P@ss!"
---
# ──── 3. Redis with password + health check ────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: production-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
      - name: redis
        image: redis:7-alpine
        command: ["redis-server", "--requirepass", "$(REDIS_PASSWORD)"]
        env:
        - name: REDIS_PASSWORD
          valueFrom:             # Read password from Secret
            secretKeyRef:
              name: redis-secret
              key: redis-password
        ports:
        - containerPort: 6379
        readinessProbe:          # Is it ready to accept traffic?
          exec:
            command: ["redis-cli", "-a", "$(REDIS_PASSWORD)", "ping"]
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:           # Is it still alive?
          exec:
            command: ["redis-cli", "-a", "$(REDIS_PASSWORD)", "ping"]
          initialDelaySeconds: 15
          periodSeconds: 20
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "250m"
            memory: "256Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: production-app
spec:
  type: ClusterIP
  selector:
    app: redis
  ports:
  - port: 6379
---
# ──── 4. Web App with health checks + auto-scaling ────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: production-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web
        image: nginx:1.25-alpine
        ports:
        - containerPort: 80
        readinessProbe:          # Don't send traffic until ready
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 3
          periodSeconds: 5
        livenessProbe:           # Restart if this fails
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
        resources:
          requests:              # HPA needs requests to calculate usage %
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "300m"
            memory: "256Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: web-app
  namespace: production-app
spec:
  type: LoadBalancer
  selector:
    app: web-app
  ports:
  - port: 80
    targetPort: 80
---
# ──── 5. HPA: Auto-scale web pods based on CPU ────
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-app-hpa
  namespace: production-app
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-app
  minReplicas: 2              # Never go below 2
  maxReplicas: 8              # Scale up to 8 under load
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50  # Scale up when CPU > 50%
bash — deploy, verify & stress test
# Deploy to the new namespace
kubectl apply -f project3-microservices.yaml

# Check everything in your namespace
kubectl get all -n production-app

# Watch the HPA (it tracks CPU usage and adjusts replicas)
kubectl get hpa -n production-app -w

# Verify health checks are working
kubectl describe pod -l app=web-app -n production-app | grep -A5 "Conditions"

# 🔥 STRESS TEST: Generate load to trigger auto-scaling!
# Open a new terminal and run:
kubectl run load-gen --image=busybox -n production-app --rm -it -- \
  /bin/sh -c "while true; do wget -q -O- http://web-app; done"

# In your other terminal, watch pods multiply!
kubectl get pods -n production-app -w

# ✅ You should see replicas go from 2 → 4 → 6 → 8 as CPU spikes!
# Stop the load gen (Ctrl+C) and watch pods scale back down.

# Clean up when done:
kubectl delete namespace production-app
🎓 What you learned

Namespaces isolate resources (teams/environments can share a cluster safely). Secrets store sensitive data (passwords, API keys) encoded — never hardcode them in YAML. Health checks (readinessProbe + livenessProbe) tell K8s when a pod is ready and when to restart it. HPA automatically scales pods based on CPU/memory — this is how Netflix, Spotify, and production apps handle traffic spikes without human intervention.

Stop EKS & Clean Up (Avoid Bills!)

⏱ ~10 min
💰 FAQ: "Can I just pause or stop my cluster?"

NO! AWS does not let you "stop" an EKS cluster. The EKS Control Plane runs 24/7 and costs $0.10/hour (~$72/month) regardless of whether you have worker nodes running or not. The only way to stop the charges is to completely delete the cluster. Because you used IaC (eksctl), recreating it tomorrow is as easy as running one command!

Always tear down when done learning. Follow your path below:

🚀 Easy Path Cleanup — One Command
bash
# Delete EVERYTHING eksctl created (cluster, nodes, VPC, roles)
eksctl delete cluster \
  --name my-first-cluster \
  --region us-east-1

# ⏳ Takes ~5-10 minutes. Wait for "cluster deleted" message.
✅ Success: You see "all cluster resources were deleted"
🔧 Manual Path Cleanup — Reverse Order

Delete in this exact order to avoid orphaned resources:

  1. Delete Kubernetes resources first (this removes the AWS Load Balancer):
    kubectl delete service nginx-service
    kubectl delete deployment nginx-deployment
  2. Delete the Node Group:
    EKS Console → Clusters → my-first-cluster → Compute tab → Select standard-workers → Click Delete. Wait until deleted.
  3. Delete the EKS Cluster:
    EKS Console → Clusters → Select my-first-cluster → Click Delete. Type the cluster name to confirm. Wait ~5 min.
  4. Delete the VPC Stack:
    CloudFormation Console → Select eks-vpc stack → Click Delete.
  5. Delete IAM Roles:
    IAM Console → Roles → Search "myEKS" → Select myEKSClusterRole → Click Delete. Repeat for myEKSNodeRole.
  6. Delete the IAM User:
    IAM Console → Users → Select eks-admin → Click Delete (if you created one).
⚠️ Critical

Delete Services BEFORE the cluster! LoadBalancer Services create AWS ELBs. If you delete the cluster first, those ELBs become orphaned and charge ~$18/month each. Always: apps → nodes → cluster → VPC → IAM.

💡 Why this step?

EKS charges $0.10/hour for the control plane alone. Add EC2, NAT, and LBs — a forgotten cluster costs $100+/month. Set a calendar reminder or AWS billing alarm!

Troubleshooting Common Issues

Stuck? Here are the most common problems beginners hit and how to fix them:

🔴 kubectl get nodes returns "No resources found"

Cause: Your kubeconfig isn't pointing to the right cluster, or nodes haven't joined yet.

Fix:

1. Re-run: aws eks update-kubeconfig --name my-first-cluster --region us-east-1

2. Check cluster status: aws eks describe-cluster --name my-first-cluster --query "cluster.status"

3. If nodes aren't joining, check the node group status in the EKS Console → Compute tab.

🔴 error: You must be logged in to the server (Unauthorized)

Cause: The AWS user in your CLI doesn't have permission to access the cluster.

Fix:

1. Verify who you are: aws sts get-caller-identity

2. Make sure this matches the user/role that created the cluster.

3. If using a different user, the cluster creator must add you: eksctl create iamidentitymapping --cluster my-first-cluster --arn YOUR_ARN --group system:masters --username admin

🔴 eksctl create cluster fails with "Cannot create cluster"

Cause: Usually missing IAM permissions or service limits.

Fix:

1. Ensure your IAM user has AdministratorAccess policy attached.

2. Check you're in a supported region (us-east-1, us-west-2, etc.)

3. Try a different region if you hit vCPU limits: --region us-west-2

🔴 Service EXTERNAL-IP stuck on <pending>

Cause: The Load Balancer is still provisioning, or nodes are in private subnets without proper tags.

Fix:

1. Wait 2-3 minutes — AWS LB provisioning takes time.

2. Check events: kubectl describe service nginx-service

3. If using manual VPC, ensure subnets have the tag: kubernetes.io/role/elb = 1 (for public subnets).

🔴 Pods stuck in Pending state

Cause: Not enough resources on your nodes, or no nodes at all.

Fix:

1. Check why: kubectl describe pod <pod-name> — look at Events section at the bottom.

2. If it says "Insufficient cpu/memory", your nodes are full. Scale up: eksctl scale nodegroup --cluster my-first-cluster --name standard-workers --nodes 3

🔴 Pods in CrashLoopBackOff

Cause: Your container is crashing immediately after starting.

Fix:

1. Check logs: kubectl logs <pod-name>

2. Check previous crash logs: kubectl logs <pod-name> --previous

3. Common causes: wrong image name, missing env vars, or the container process exits immediately.

🔴 aws configure — "Unable to locate credentials"

Cause: You haven't run aws configure yet, or credentials are expired.

Fix:

1. Run aws configure and paste your Access Key + Secret Key.

2. If keys are expired, create new ones in IAM Console → Users → Security credentials → Create access key.

3. Verify: aws sts get-caller-identity

🔴 eksctl delete cluster hangs or fails

Cause: Orphaned resources (usually LoadBalancers or security groups with dependencies).

Fix:

1. Delete all Services first: kubectl delete svc --all

2. Wait 2-3 min for ELBs to de-provision, then retry delete.

3. If still stuck, go to CloudFormation Console and manually delete the eksctl stacks (they start with eksctl-my-first-cluster).

AWS ALB Ingress Controller

By default, exposing a service via type: LoadBalancer creates a brand new AWS Classic/Network Load Balancer for every single app. This is extremely expensive! The AWS Load Balancer Controller allows you to use a single Application Load Balancer (ALB) to route traffic to dozens of apps using path-based routing (an Ingress).

Step 1: Create IAM OIDC Provider

Your cluster needs an IAM OIDC provider so that Kubernetes service accounts can assume AWS IAM roles (IRSA).

Terminal 
eksctl utils associate-iam-oidc-provider \
    --cluster my-eks-cluster \
    --approve
Step 2: Create IAM Policy and Role

Download the IAM policy for the AWS Load Balancer Controller and create the IAM role.

Terminal 
# Download IAM policy
curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.5.4/docs/install/iam_policy.json

# Create IAM policy
aws iam create-policy \
    --policy-name AWSLoadBalancerControllerIAMPolicy \
    --policy-document file://iam_policy.json

# Create IAM Service Account (IRSA)
eksctl create iamserviceaccount \
  --cluster=my-eks-cluster \
  --namespace=kube-system \
  --name=aws-load-balancer-controller \
  --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn=arn:aws:iam::YOUR_ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve
⚠ IMPORTANT: Replace YOUR_ACCOUNT_ID with your actual 12-digit AWS account ID.
Step 3: Install the Controller using Helm

Helm is the package manager for Kubernetes. We will use it to install the controller.

Terminal 
# Add the EKS Helm repo
helm repo add eks https://aws.github.io/eks-charts
helm repo update

# Install the controller
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=my-eks-cluster \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=us-east-1 \
  --set vpcId=YOUR_VPC_ID
Step 4: Create an Ingress for 2048

Now, instead of type: LoadBalancer, create an Ingress rule to route traffic to your 2048 game.

ingress-2048.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  namespace: game-2048
  name: ingress-2048
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
        - path: /
          pathType: Prefix
          backend:
            service:
              name: service-2048
              port:
                number: 80
Terminal 
kubectl apply -f ingress-2048.yaml
kubectl get ingress/ingress-2048 -n game-2048

Wait a few minutes, copy the ADDRESS from the output, and paste it into your browser!
